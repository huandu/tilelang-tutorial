# 示例 2：低精度对拍的容差从哪来

## 目的

正确性对拍最后一定会落到一行断言：`atol`、`rtol` 取多少？“±1e-3”这种数字如果是
抄来的，出了问题既不敢放宽也不知道能收紧。这个脚本把容差拆成三层：

1. **机器精度**：从 IEEE-754 的有效位数算出 fp16 / bf16 / fp32 的 `u = 2^-p`；
2. **归约预算**：长度 K 的 dot / GEMM-K 维，输入舍入误差相对 `S = Σ|a_i·b_i|`
   的最坏情形是 `u`，均方根是 `u/√K`；
3. **实测分布**：`fp16/bf16 输入 + fp32 累加` 的 dot 与 fp64 精确值比较，看实测
   中位数与预算是否同量级。

它证明的是“容差的数量级从哪来”，**不是**“某个 kernel 一定通过某个容差”——后者
取决于你的数据分布、归约顺序和累加类型，必须在有卡机器上实测。

## 运行前提

* Python 3.9+ 与 numpy（TileLang 自身也依赖 numpy）。
* 不需要 GPU/NPU。

## 运行命令

```bash
python3 chapters/12-debugging-and-profiling/code/02-tolerance-model/tolerance_model.py
python3 tolerance_model.py --lengths 128,512,2048 --trials 4000
```

**判据**：“中位数/预算”这一列稳定在 0.5 左右，说明 `u/√K` 这个量级模型可用；
若它偏离一个数量级以上，说明数据分布或者累加类型与模型假设不符。

## 这张表怎么用在真实对拍里

* 上表的基准是 `S = Σ|a_i·b_i|`。日常断言用的是“相对结果”口径，
  当数据零均值时 `S / |Σa_i·b_i| ≈ √K`，所以长归约的相对误差可以放大到 `u·√K`
  （fp16、K=4096 约 3e-2），**因此长归约必须配 atol 兜住接近零的输出**。
* 工程起点：fp16 用 `rtol=1e-3, atol=1e-3`；bf16 用 `rtol=1e-2, atol=1e-2`；
  再配 `max_mismatched_ratio≈1e-3` 允许极少数离群元素。
* 这与锁定版本里两个对拍工具的缺省量级一致：
  `torch_assert_close(rtol=1e-2, atol=1e-3, max_mismatched_ratio=0.001)` 与
  `Profiler.assert_allclose(atol=1e-2, rtol=1e-2, max_mismatched_ratio=0.01)`。

## 注意事项

* 本脚本用“截掉 fp32 低 16 位尾数”近似 bf16 舍入，与硬件的 round-to-nearest-even
  有微小差异，只影响第三位有效数字，不影响数量级结论。
* 这只覆盖了“输入舍入”这一主项。真实 kernel 还可能有累加顺序、分块累加（split-K）、
  以及 epilogue 中额外的 cast 误差，需要在有卡机器上用固定输入实测。
