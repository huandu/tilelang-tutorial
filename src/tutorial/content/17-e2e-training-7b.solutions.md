# 第 17 章 习题答案

每题给出**解题思路**、**参考答案**与**常见错误**。编号与 `exercises.md` 一一对应。

---

## E1

**思路**：把每个参数的字节数加总，再乘参数量，最后换算单位。

**参考答案**：每个参数占用 `2（权重）+ 2（梯度）+ 4（m）+ 4（v）+ 4（主权重）= 16`
字节。总量 `7.61e9 × 16 = 1.2176e11` 字节。除以 `1024³`：
`1.2176e11 / 1.0737e9 ≈ 113.4 GiB`。

单张 80GB 卡（实际约 80×10⁹ 字节 ≈ 74.5 GiB 可用）连 113.4 GiB 的参数与优化器状态都
放不下，更不用说激活值、通信缓冲与碎片。所以必须分片（ZeRO/FSDP）：8 卡均摊后每卡
约 14 GiB。

**常见错误**：用 `1000³` 而不是 `1024³`（差 7%）；把「80GB」当成 80 GiB；忘了
fp32 主权重（漏掉会少算 28 GiB）。

## E2

**思路**：从「一次乘加 = 2 FLOPs」和「反向约为前向两倍」推出。

**参考答案**：前向每个参数每 token 约 2 FLOPs；反向要对权重和对输入各求一次梯度，
共约 4 FLOPs；合计 6。它忽略了 attention 中与序列长度平方成正比的项（`Q·Kᵀ` 和
`softmax·V` 的开销）。当**上下文很长**时估算偏低，例如 128K 上下文下的 attention
会占据可观比例的算力，此时 `6ND` 只反映参数相关部分，需要单独加上 attention 的
`O(B·H·S²·d)` 项。

**常见错误**：说「6 是经验常数」而不给推导；忘记说明适用范围。

## E3

**思路**：围绕「初始化来源」「token 数」「成本」「风险」四个维度对比。

**参考答案**：

| | 路线 A 小规模预训练复现 | 路线 B 从开源权重继续训练 |
| --- | --- | --- |
| 初始化 | 随机 | 现成权重 |
| 需要 token | 百亿级才看到效果 | 十亿级可能有领域效果 |
| 成本 | 高 | 低（可用 LoRA 更低） |
| 主要风险 | 训不出能力、成本高 | 灾难性遗忘、初始化不可解释 |

本教材先用 A 验证链路，是因为 A 的每一步都在你的控制里——数据、初始化、loss 曲线
都是你自己造的，一旦出错容易定位；用 A 把数据管线、训练循环、kernel 都验证过之后，
再用 B 做出「有实际作用」的结果，风险最小。

**常见错误**：把两条路线说成互斥；忽略路线 B 的遗忘风险。

## E4

**思路**：直接读源码里的字节数常量。

**参考答案**：

1. 权重 2、梯度 2、m 4、v 4、主权重 4（字节/参数）。
2. `fp32_master=False` 后每参数 12 字节：`7.61e9 × 12 = 9.132e10` 字节 ≈ **85.05 GiB**。
3. 因为优化器状态（m+v+主权重 = 12 字节/参数）占总量的 75%，压它收益最大；
   压权重（只有 2 字节/参数）收益最小且直接影响精度。

**常见错误**：以为 `fp32_master` 不影响计算；算错单位。

## E5

**思路**：从「算力浪费」与「内存约束」两个角度解释设计动机。

**参考答案**：

1. padding 会带来真实算力浪费（填充 token 不产生有效梯度）并污染 attention 统计；
   丢弃不到一条序列的尾块，损失的 token 比例极低（< 一个 block），是更划算的取舍。
2. 流式数据无法全部读进内存，所以只能做带缓冲的局部 shuffle；buffer 越大越接近均匀，
   但内存与首次填充延迟也越大。
3. **不一样**。buffer 大小改变了「抽取哪个文档」的随机序列，所以相同 `seed` 下输出
   仍会不同。可复现性要求 `seed` **和** `buffer_size` 都固定。

**常见错误**：认为固定 seed 就能保证任意 buffer 下输出一致。

## E6

**思路**：对照 `out_idx` 的语义与 autograd 的机制。

**参考答案**：

1. `2` 是输出参数在参数列表中的下标（0-based，`X`、`W`、`Y` → `Y` 是 2）。
   换成 `[-1]` **等价**：负数下标会被合法化为 `len(params) - 1`
   （见 `tilelang/jit/adapter/base.py:27-53`）。
2. 保存的是**输入张量** `x`、`w` 的引用（不新分配），供反向使用。反向需要 `x` 来算
   `rstd`；保存而不是在 forward 里额外返回，是为了让 autograd 知道这些张量参与了本算子。
3. `backward` 返回全 `None` 时，`x`、`w` 会得不到梯度（`x.grad`/`w.grad` 保持为
   `None` 或旧值），训练不会更新这两个参数——loss 会很快不再下降。这是一个「静默出错」
   的典型，必须靠 M4 的数值对齐检查发现。

**常见错误**：把 `out_idx` 当成「第几个输出是第几个返回值」以外的含义；忘记反向返回
的个数必须与 `apply` 的输入个数匹配（含 `eps` 的 `None`）。

## E7

**思路**：从「TileLang 是什么」出发：它生成的是前向 device 代码，没有在 host 侧建立
自动微分图。

**参考答案**：TileLang 是 kernel DSL，产出的是设备端函数与调用包装；它不追踪张量运算、
不维护计算图，因此无法像 PyTorch 算子那样自动求导（v0.1.15 的 `tilelang/` 目录里没有
任何 autograd 相关代码）。

两种补法：

1. **包进 `torch.autograd.Function`，反向用 PyTorch 写**：优点是最快落地、数值容易对；
   缺点是反向没有 kernel 加速，而反向计算量本就更大。
2. **再写一个 TileLang 反向 kernel**：优点是全程留在加速器上、性能最好；缺点是要自己
   推导并验证 `dx`/`dw`，出错风险高。

**常见错误**：声称 TileLang 会自动处理 autograd；只提方案不给代价。

## E8

**思路**：在 `pack` 的循环里判断「放不下就换下一条」。

**参考答案**：核心改动是：对每篇文档先 `encode`，拿到长度 `L`；如果 `len(buf) + L + 1 >
block_size`，则先把 `buf` 产出（若它非空且不足整块则丢弃并累加浪费计数），再开始把这篇
文档放进新 `buf`。示例代码：

```python
def pack_no_cross(encode, docs, eos_id, block_size):
    buf, wasted = [], 0
    for doc in docs:
        ids = encode(doc) + [eos_id]
        if len(buf) + len(ids) > block_size:
            if buf:
                wasted += len(buf)
            buf = []
        buf.extend(ids)
        while len(buf) >= block_size:
            yield buf[:block_size]
            del buf[:block_size]
```

**代价**：每条序列内部不再跨文档，但序列之间会浪费掉「放不下」的那一段（`wasted`），
整体有效 token 比例下降，等于把算力花在了「空位」上——这正是 padding 想避免的问题的
另一种形式。取舍取决于你对「序列纯净度」的要求。

**常见错误**：直接用 `while len(buf) < block_size: buf.append(pad)`，那就变成了 padding。

## E9

**思路**：把参数量换成 0.5B 再跑脚本。

**参考答案**：由于 Qwen2.5-0.5B 的结构参数不在 corpus 内，答题时可用一个
「名义 0.5B」的 `ModelSpec`（把 `params=0.5e9`）代入 `memory_bytes`：

```
每参数 16 字节 × 0.5e9 = 8e9 字节 ≈ 7.45 GiB
```

命令（示意）：

```bash
python3 -c "import train_plan as t; print(t.to_gib(sum(t.memory_bytes(0.5e9, t.TrainState()).values())))"
```

**结论**：7.45 GiB 的参数+优化器，单张 40GB 卡在**不考虑激活值**时绰绰有余；考虑激活值
与分片后，0.5B 单卡训练完全可行——这就是 §10 把它放在 L2 的原因。

**常见错误**：忘了 0.5B 也含 embedding，参数量要用实际值而非「0.5e9」的近似；
以为显存账本可以完全忽略激活值。

## E10

**思路**：梯度累积在数学上等价于把多个 micro-batch 的梯度求和（再按等效 batch 缩放）。

**参考答案**：实现方式是固定模型初始权重，分别用两种配置各跑一次 `backward`，比较
`lm_head.weight.grad` 的**范数相对差**：

```python
def grad_norm(model):
    return model.lm_head.weight.grad.detach().float().norm().item()

# 配置 1：micro_batch=8, grad_accum=1
# 配置 2：micro_batch=2, grad_accum=4
rel = abs(g1 - g2) / max(g1, g2)
assert rel < 1e-4   # fp32 下可收到 1e-4；bf16 下放宽
```

**判据**：`rel < 1e-4`（fp32）。**允许少量误差**：不同 micro-batch 的样本不同，
求和顺序不同会带来浮点非结合性误差；bf16 下这个误差会更大，门限要放宽。

**常见错误**：忘了除以 `grad_accum` 做缩放；门限设成 `0`；在两种配置里用了不同的
随机数据导致本就不可比。

## E11

**思路**：分别读两端代码里的归约与并行原语。

**参考答案**：

1. NV 版用 `T.reduce_sum(..., dim=1)` 做整行归约；昇腾版用
   `T.alloc_reducer` + `T.reducer_init` + `T.reducer_update` + `T.finalize_reducer`
   显式声明一个 reducer，配合 `T.SimtVF` 的线程域与 `T.Pipelined` 的多缓冲。
2. `annotate_buffer_versions` 声明每个 UB buffer 用几份（多缓冲深度）；
   `T.SimtVF(threads=...)` 定义一个 SIMT 线程域，让 `T.Parallel` 在里面并行且可向量化。
3. 最需要关注的是**归约/同步/缓冲**这三类与硬件模型强相关的写法——它们恰恰是跨硬件
   不可直接复用的部分，其他大部分 tile 级结构可以照搬。

**常见错误**：以为昇腾版和 NV 版只是换了个 target；忽略了多缓冲与显式 reducer 的差异。

## E12

**思路**：把 §7.3、§7.4、§9 的验收条目整理成清单，每条要可执行、有门限。

**参考答案**：

1. **前向数值对齐**：随机输入下 `allclose(y, ref, rtol=atol=2e-2)`（bf16）。
2. **反向来源**：写明反向是「torch 公式」还是「自写 kernel」，并把它包进
   `torch.autograd.Function`——确认 `x.grad`/`w.grad` 在 `backward` 后**不为 `None`**。
3. **反向数值对齐**：相对 L2 误差 `< 5e-2`（bf16），并用多个真实宽度（如 3584、896）
   的 shape 复测。
4. **端到端 loss 对齐**：同一批 token、同一权重，`|loss_new − loss_ref| / loss_ref < 1e-3`；
   再跑 100 步确认两条 loss 曲线在统计误差内重合。
5. **吞吐不下降**：用同一 profiler 口径（如第 12 章）比较替换前后 tokens/s；若下降说明
   kernel 反而拖慢了，回退。

**常见错误**：只测前向不测反向；门限一刀切；只看 1 步 loss 不看曲线。

## E13

**思路**：GPU 空转说明「算的时刻没到数据」，属于供给问题而非计算问题。

**参考答案**：优先排查：`DataLoader` 的 `num_workers`（CPU 预处理是否串行成为瓶颈）、
tokenizer 是否在训练循环里同步执行、packing 是否在线做（应提前/并行做）、
以及磁盘/网络读取是否阻塞。因为问题出在「喂不进去」，改 kernel 只会让本来就空闲的
计算单元更快——对利用率没有帮助。**先确认瓶颈在哪一环，再动手优化那一环。**

**常见错误**：看到利用率低就去调 kernel；忽略数据加载是串行的。
