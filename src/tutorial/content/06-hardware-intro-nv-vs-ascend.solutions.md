# 第 06 章 习题答案

说明：每题给出**解题思路**、**参考答案**与**常见错误**。动手题的答案给出思路与关键
数据，不代替读者在自己机器上运行。

---

## E1 概念题 ★

**思路**：把“慢”拆成延迟、容量、带宽三个量，再说明片上存储和分块各解决哪一个。

**参考答案**

1. 访存的延迟比算术大两个数量级：CUDA 官方文档说未缓存访存有“hundreds of clock
   cycles”，而算术指令约 4 个周期（compute capability 7.0）。若每次都去 HBM 取数，
   计算单元大部分时间在等待。片上存储的作用就是**把马上要算的数据搬到延迟更低的层级**。
   三个量的规律是：越靠近计算单元，延迟越低、带宽越高、**容量越小**。
2. 片上存储解决“慢”；分块解决“小”。因为片上容量有限，不可能把整个张量放进去，
   只能切成 tile 轮流上片。
3. 分块后，一块 `A` 子矩阵被多个输出 tile 复用。**一次 HBM 读入，换来多次片上计算**；
   复用次数越高，单位计算需要的 HBM 字节数越少。对矩阵乘，一个 `block_M × block_K`
   的 `A` tile 会被 `N/block_N` 个输出 tile 复用。

**常见错误**：把“带宽”和“延迟”混为一谈。带宽决定“搬一批要多久”，延迟决定
“第一个字节要等多久”；片上存储主要赢在延迟和带宽两者，但因为容量小，必须分块。

## E2 概念题 ★

**思路**：按“谁给谁用”配对，再找出一对不是同名对应的。

**参考答案**

| NV | 昇腾 | 是否对应 | 说明 |
| --- | --- | --- | --- |
| 寄存器 | （Cube/Vector 内部寄存器） | 大致对应 | 都是最靠近计算单元的私有存储 |
| shared memory | **UB + L1** | **不是一对一** | UB 服务 Vector/标量，L1 服务 Cube；同名的一个概念在昇腾上拆成两种角色 |
| L2 | L2 Cache | 对应 | 都是核外、被多个核共享的片上缓存 |
| HBM | GM | 对应 | 都是外部显存 |
| （无同名对应物） | **L0A / L0B / L0C** | **不是对应物** | 这是 Cube 专用的输入/输出存储，NV 侧没有同名结构；最接近的是 Tensor Core 的操作数/累加器存储（寄存器 fragment，或 Blackwell 的 Tensor Memory），但命名与粒度都不同 |

所以“哪一对不是真正的对应物”至少有两处：**shared memory ↔ UB/L1**（一对多），
以及 **L0A/L0B/L0C ↔ 无**（NV 侧没有同名物）。

**常见错误**：把 UB 直接当成 shared memory、把 L0C 当成 L2。判据是“谁访问它”：
UB 是 Vector/标量的输入输出，L0C 是 Cube 的累加器。

## E3 概念题 ★

**思路**：用第 1 章的公式直接算。

**参考答案**

1. 运算量 $= 2MNK = 2 \times 4096^3 \approx 1.374\times10^{11}$ FLOP。
2. 最小访存量（fp16，2 字节）= $(MK + KN + MN)\times2$
   $= 3\times 16{,}777{,}216 \times 2 = 100{,}663{,}296$ 字节 $\approx 96$ MiB。
3. 朴素实现里，每个输出元素要读 `A` 的一行（$K$ 个元素）和 `B` 的一列（$K$ 个元素），
   总读元素数 $= MN\cdot2K = 2\times4096^3 \approx 1.374\times10^{11}$，合
   $2.75\times10^{11}$ 字节 $\approx 256$ GiB。放大倍数
   $= \dfrac{2MNK\cdot2}{(MK+KN+MN)\cdot2} = \dfrac{2K}{3} \approx 2731$ 倍。
4. 靠**分块 + 片上复用**：把 `A`、`B` 的子块搬到片上，在同一块上完成多个输出的计算，
   使同一份数据只从 HBM 读一次。

**常见错误**：忘记 fp16 是 2 字节，或把“读 `A` 的行 + 读 `B` 的列”算成 $K$ 而不是
$2K$ 个元素。

## E4 概念题 ★

**思路**：分别找“NPU 不只有 SIMD”和“GPU 不只有 SIMT”的厂商证据。

**参考答案**

两条来自厂商来源的反例：

1. **昇腾硬件页**写明昇腾 950PR“支持 SIMD+SIMT 混合编程架构”（`references.md` R9）；
   **CANN 文档**给出了 AI Core 的 SIMT 抽象模型（线程、线程块、Data Cache），并说明
   SIMT“目前仅支持 Atlas 350 加速卡”，而 Atlas 350 采用 Ascend 950PR（R8、R12）。
   这反驳“NPU = SIMD”这一半。
2. **NVIDIA Hopper 官方资料**把异步搬运（TMA）、专用矩阵单元（Tensor Core）、
   warp specialization、thread block cluster 都放进同一套执行体系（R1、R2）。
   同一份程序里，通用线程走 SIMT，Tensor Core 走 warpgroup/CTA 级矩阵指令，TMA 由
   单个线程驱动硬件。这反驳“GPU = SIMT”这一半。

另一条锁定源码层面的证据：TileLang 昇腾方言在同一 kernel 里提供 `T.SimtVF` 与
`T.SimdVF`（S8），其 README 明说支持混合（S1）。

**常见错误**：只举 TileLang 的例子而不举厂商硬件的例子。题目要求厂商来源，是因为
“支不支持 SIMT”首先是一个硬件/CANN 事实，语言 API 只是它的映射。

## E5 代码阅读题 ★★

**思路**：逐个 API 对照本章的四个维度表。

**参考答案**

1. `T.alloc_shared` → **shared memory**（scope `shared.dyn`）；`T.alloc_fragment` →
   **寄存器累加器**（scope `local.fragment`）。出处：S2。
2. 对应 1.4 节的**多缓冲**：开 3 份缓冲让搬运与计算重叠。代价是**占 3 倍的片上空间**，
   受 shared memory 每 block 上限（H100 227 KB）约束；同时需要更多同步。
3. Hopper 上可能是 **`wgmma`**（第 2 代），Blackwell 上可能是 **`tcgen05`**（第 3 代）。
   出处：S6 的 `T.gemm` docstring（“On Hopper ... WGMMA ... On Blackwell TCGEN5MMA ...”）。
   注意是“可能”，具体由编译器根据 target 和操作数 scope 选择。
4. 关掉的是 **TMA 降级路径**：`disable_tma=True` 让这次拷贝不走 TMA，退回普通 SIMT
   拷贝/其他路径。出处：S4。

**常见错误**：以为 `T.gemm` 一定生成某一条固定指令。它是一条**可降级**的高层 tile op，
实际指令由后端选择（第 14、24、25 章展开）。

## E6 代码阅读题 ★★

**思路**：对照本章 4.3 节的 MTE 表。

**参考答案**

1. `T.copy(A[..], A_l1)`：**MTE2**，路径 `GM → L1`。
2. `T.gemm(A_l1, B_l1, C_l0c, ...)`：**隐含 MTE1 搬运**（`L1 → L0A/L0B`）+ **Cube**
   矩阵计算，结果写入 L0C。MTE1 就是“把 L1 上的 A/B tile 搬到 Cube 的输入 buffer”。
3. `T.dual_copy(C_l0c, C_ub)`：**Fixpipe**，路径 `L0C → UB`；按源码语义，这是一次
   硬件双目标拷贝，把 tile 沿 M（或 N）拆给两个 AIV（S5）。
4. `with T.SimtVF(threads=128):`：进入 **Vector 核（AIV）上的 SIMT 区域**；循环体里的
   `T.Parallel` 是逐元素 ReLU，跑在 Vector 上。
5. `T.dual_copy(C_ub, C[...])`：**MTE3**，路径 `UB → GM`。

**常见错误**：把第 3 步当成 `L0C → GM`（那是 Fixpipe 的另一条路径）；把 `T.gemm`
当成只有计算、不含搬运（它隐含 L1→L0 的 MTE1）。

## E7 概念题 ★★

**思路**：用“累加器住哪”当主线。

**参考答案**

| 代际 | 指令 | 粒度 | 累加器 `D` | 同步方式 |
| --- | --- | --- | --- | --- |
| 1 | `mma.sync` | warp（32 线程） | 寄存器 fragment | 同步（指令返回即完成） |
| 2 | `wgmma.mma_async` | warpgroup（4 个连续 warp = 128 线程） | 寄存器 fragment | `wgmma.fence` / `commit_group` / `wait_group` |
| 3 | `tcgen05.mma` | CTA（可选 2-CTA） | **Tensor Memory（TMEM）** | `mbarrier`（完成通知） |

演进主线：第 1 代把操作数和累加器全放寄存器，寄存器压力限制 tile 大小；第 2 代把操作数
（A 可进寄存器或 shared，B 在 shared）和“发射/完成”分离，换来更大 tile 和更深流水；
第 3 代把累加器搬进专用 TMEM，进一步释放寄存器。

TMEM 结构：`sm_100a`/`sm_100f` 上为每 CTA **512 列 × 128 行**，每个 cell 32-bit
（R5，9.7.18.1）。

**常见错误**：说 `wgmma` 的累加器在 TMEM（那是 `tcgen05`）；或把 warpgroup（128 线程）
与 warp（32 线程）混淆。

## E8 代码阅读题 ★★

**思路**：先想清楚“谁会被谁覆盖”，再看那一行表达的是哪个方向。

**参考答案**

1. 它表达**缓冲归还**约束：第 $i$ 轮要复用的 slot（`i % versions`）上一次是被第
   $i - versions$ 轮占用的，只有当那一轮的 copy-out 结束后，这个 slot 才空出来。
   因此 copy-in 最早只能在 `copy_out[i - versions]` 结束时开始。
2. 删掉后，模型会认为任何一轮的 copy-in 都可以随时开始，于是算出“几乎完美重叠、
   利用率接近 100%”的**过于乐观**结果。真实硬件上，这意味着第 $i$ 轮的 MTE2 会覆盖
   第 $i - versions$ 轮还没被消费完的数据，结果是读到了错误的（新）数据，典型的
   **读后写（RAW 反向）竞争**，而且往往只在某些时序下出现。
3. 至少三条可接受的遗漏：Set/Wait 指令本身的开销；队列深度/发射间隔限制；DMA 带宽上限
   （copy 时间其实随数据量和带宽变化）；流水填充与排空（tail）；片上容量与版本数的耦合。

**常见错误**：把这一行理解成“正向数据就绪”。正向就绪是“compute 等 copy-in”，
由 `ms = max(prev_compute_end, copy_in_end)` 表达；`reuse_ready` 是反方向。

## E9 动手题 ★★

**思路**：先跑数，再用“机器平衡点”解释差异。

**参考答案**（以下为脚本在 macOS / Python 3.11 上的实际输出）

1. 默认（copy_in=10, compute=4, copy_out=10）：

   * `versions=1`：makespan 144，利用率 16.7%；
   * `versions=2`：makespan 82，利用率 29.3%。

2. `--compute 40`（copy_in=10, copy_out=10）：

   * `versions=1`：makespan 360，利用率 66.7%；
   * `versions=2`：makespan 260，利用率 92.3%（`versions=3` 相同）。

3. 解释：第一种负载是 **memory-bound**，搬运时间约是计算时间的 5 倍，即便完美重叠，
   利用率上限也只在 `compute / (copy_in + copy_out) = 4/20 = 20%` 附近，所以提升有限。
   第二种负载是 **compute-bound**，计算时间约是搬运时间的 2 倍，串行基线已经到 66.7%，
   多缓冲把搬运藏进计算背后，利用率升到 92.3%。用第 1 章的话：算子的算术强度相对机器
   平衡点处于哪一侧，决定了优化方向。
4. 一组“几乎没有提升”的参数：`--copy-in 1 --compute 20 --copy-out 1`。实测
   `versions=1` 利用率 90.9%，`versions=2` 98.4%。因为搬运本来就小，串行实现已经
   接近计算瓶颈，多缓冲只能吃掉最后一点空隙。

**常见错误**：只看 makespan 变小就断定“优化有效”，却不看利用率上限由负载决定。
另一个错误是把“多缓冲一定更快”当成普遍规律，当计算本身很快、数据很小时，多开缓冲
反而浪费片上空间（见本章 7.1、7.3）。

## E10 动手题 ★★

**思路**：字节数 = 元素数 × dtype 字节宽 × 版本数。

**参考答案**

1. `C_ub(128,256)` fp32 = $128\times256\times4 = 131{,}072$ 字节 = 128 KiB。
   1 份 128 KiB（放得进 192 K）；2 份 256 KiB（**放不进**，超出 64 KiB）。
2. 2 份缓冲时每个版本最多 $192\,\text{KiB}/2 = 96$ KiB。fp32 每元素 4 字节，所以
   元素数上限 $= 96\times1024/4 = 24{,}576$。例如 `128×192` 正好是 24576 个元素。
3. 换成 fp16（2 字节）后，每版本元素数上限翻倍到 49,152，例如 `128×384`；或者同样
   形状下占用减半。
4. 不能直接用。`192 K` 是某份官方文档在讲 bank 冲突时对**某一型号**的示例，不是昇腾
   家族通用规格（R10）。正确做法是在真实设备上用 `GetCoreMemSize` 查询（R6）。

**常见错误**：把 192 K 当成 192000 而不是 192×1024；或者忽略“版本数”这个乘数。

## E11 概念题 ★★

**思路**：把一个 buffer 的生命周期想成“谁写、谁读、什么时候可以被下一个人写”。

**参考答案**

1. 正向（数据就绪）：`MTE2 → MTE1`，MTE2 写完 L1 的 slot 后 SetFlag，MTE1 在读取前
   WaitFlag。反向（缓冲归还）：`MTE1 → MTE2`，MTE1 读完该 slot 后 SetFlag，MTE2 在
   下一次覆盖该 slot 前 WaitFlag。出处：S13（TileLang-Ascend 编程指南“同步原语”）。
2. 只有正向信号时，只能保证“读者等到写者完成”，但**保证不了“写者等到读者完成”**。
   在第 2 轮要覆盖 slot 0 时，如果第 0 轮的 Cube/Vector 还在读 slot 0，MTE2 就会把新
   数据写过旧数据。这个方向必须用反向信号单独表达。
3. 工程含义：**event id 是“有向边”上的资源，不是全局编号**。因为 `A → B` 和 `B → A`
   是两条独立的边、两个独立的编号空间，所以正反两对可以各自从 0 开始编号而不冲突。
   这样做的价值是编号空间更小、更易读；但要小心同一方向上不同语义的信号（如 `FREE`
   与 `READY`）必须分开命名。

**常见错误**：以为 SetFlag/WaitFlag 是“屏障”。它们是**成对的有向信号**，不是
`barrier`。另外，`WaitFlag` 会清标志位，所以一个 Set 只能被一个 Wait 消费。

## E13 动手题 ★★★（GPU，可选）

**思路**：先在 GPU 上跑通，再从生成代码里回答本章的结构问题。

**参考答案（要点）**

* 把 kernel 从 `try/except` 里取出后，用一段 `@tilelang.jit` 的函数 + `torch` 输入调用。
  正确性判据：与 `torch.relu(a.float() @ b.float())` 在 `rtol=1e-2, atol=1e-2` 内相等。
* 生成代码的观察点：

  * Hopper 通常给出 `wgmma`；Blackwell 通常给出 `tcgen05`（见 S6）；
  * `T.copy` 在合适形状下会走 TMA（除非 `disable_tma=True`，S4）；
  * `num_stages=3` 通常对应 3 份 shared buffer，但具体版本数由编译器与容量约束决定。

* 必须记录 GPU 型号、CUDA 版本、TileLang commit，并把验证级别写成“在真实硬件上运行过”。

**常见错误**：把“跑通”写成“达到了某个性能”。正确性和性能是两件事；性能必须给出
shape、dtype、是否含 epilogue 与测量工具。

## E14 动手题 ★★★（NPU，可选）

**思路**：跑通 → 取 trace → 用硬件事实解释。

**参考答案（要点）**

* 按后端 README 的 Quick Start（$M=256, N=7168, K=2048$）跑通，与
  `torch.relu(a.float() @ b.float().T)` 对照（S1）。
* trace 观察点：

  * Cube（AIC）与 Vector（AIV）在时间线上是否重叠，理想情况下 GEMM 与 ReLU 应有交叠；
  * MTE1/MTE2/MTE3 是否有长时间空等，说明哪条流水是瓶颈；
  * 编译器插入的 Set/Wait 是否与手写的 `T.set_flag`/`T.wait_flag` 吻合（S11、S13）。

* 用 `GetCoreMemSize` 记录 UB/L1/L0C 真实容量，回填 E10 的示例数字。

**常见错误**：把 msProf 的某次采样当成通用结论；或忘记 CANN/torch_npu 版本，导致
结论无法复现。另一个常见错误是把本章的“示例容量”（UB 192 K、L1 512 KB）当成设备
真实值，必须用 `GetCoreMemSize` 实测。
