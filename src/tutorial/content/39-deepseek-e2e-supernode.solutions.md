# 第 39 章 习题参考答案

每题的答案都写明**依据在哪一章**。本章不引入新结论，因此这里给出的答案
应该都能在正文或前面的章节里找到对应段落。

## E1

**思路**：先回想 MoE 的四段结构（第 16 章 §2.3–§2.5），再问「哪两段不做算术」。

**答案**：**dispatch** 与 **combine** 是零 FLOP 的搬运。

字节量公式是「每 token 每方向 `k·d·b`」（第 16 章 §2.6 第 3 条、
第 38 章 §1.2）：

* `k` —— 一个 token 被路由到的专家数（top-k）；
* `d` —— hidden 维度；
* `b` —— 每个元素的字节数（dispatch 用 FP8 时 `b=1`，combine 用 BF16 时 `b=2`）。

代入 DeepEP 的测试条件（`k=6, d=7168`）：dispatch 是
`6×7168×1 ≈ 42 KB`，combine 是 `6×7168×2 ≈ 84 KB`（第 38 章 §1.2）。
乘上 16384 tokens/rank，一层就是 GB 量级；而同一层的 grouped GEMM 在默认
形状下只有约 2.9 TFLOP 的账（第 16 章 §2.4），两者同量级。

**常见错误**：只说「因为要跨卡搬运」而不给公式。跨卡是**为什么贵**，
`k·d·b` 才是**贵多少**。

## E2

**思路**：把式 (20) 的符号逐一对应回论文语境。

**答案**：

1. `n` 是超连接的展开率（论文用 `n=4`），`L` 是总层数。`L_r` 是重算块包含的
   层数（`../tilelang-corpus/14-deepseek-ascend-stack/raw/paper-deepseek-mhc.md:504-539`）。
2. 约束是：**重算块不能跨流水线的 stage 边界**，所以论文把重算边界与流水线
   stage 对齐（`...:539`）。原因是重算过程依赖每个 stage 的初始激活
   `x_{l0}`，而这个激活是**按 stage 缓存在本地**的；跨 stage 会把这份缓存关系
   打破，也会和 §4.3.3 的通信重叠冲突。
3. 细节是：**残差在层间要先回 bf16 再转回 fp32**
   （`../tilelang-corpus/14-deepseek-ascend-stack/raw/TileKernels/tile_kernels/mhc/multilayer_recompute_cuda.py:111-112`）。
   因为前向保存下来的下一层输入就是 bf16，重算必须复现这个精度往返，
   否则数值对不上（第 34 章 §6.5）。

**常见错误**：把 `L_r*` 当成「越大越好」或「越小越好」。它是**峰值显存**的
最小点，而峰值显存由「常驻的 `nC·⌈L/L_r⌉`」与「瞬时的 `(n+2)C·L_r`」
两项之和决定——两项一个随 `L_r` 减小而增大、一个随之增大。

## E3

**思路**：第 38 章 §9.3 有一张现成的三层表。

**答案**：

| 层次 | 重叠的是什么 | 谁负责 |
| --- | --- | --- |
| kernel 内 | dispatch 的 issue 与本地拷贝；combine 的发送与归约 | DeepEP-Ascend 的 Ascend C kernel |
| 调用级 | 「这一次 dispatch」与调用方后续的独立计算 | 使用者的代码（`defer_epilogue` + `async_with_compute_stream`） |
| 流水线级 | 前向 chunk 与反向 chunk 的计算-通信 | DualPipe 的调度骨架 |

mHC 论文 §4.3.3 是在**流水线级**上加了规则：把 MLP 层的 `ℱ_post,res` kernel
放到专用高优先级 compute stream（以免阻塞通信流），并且让 attention 层的
长算子不使用 persistent kernel（以便被抢占）。论文同时说明，重算过程与流水线
通信解耦，因为 `x_{l0}` 已经缓存在本地（`../tilelang-corpus/14-deepseek-ascend-stack/raw/paper-deepseek-mhc.md:541-563`）。

**常见错误**：把 `defer_epilogue` 归到「流水线级」。它是**调用级**的机制。

## E4

**思路**：第 38 章 §3.4 有一条硬约束，直接对应这三行。

**答案**：

1. 第 1 行（`dispatch`）与第 3 行（`combine`）是一对：一次 MoE 的前向里，
   dispatch 把 token 送出去、combine 把结果收回来。第 2 行
   （`shared_expert(x)`）是与通信重叠的那段独立计算。
2. 只设 `defer_epilogue=True` 而不设 `async_with_compute_stream=True`，
   **C++ 侧会直接断言失败**——依据是
   `../tilelang-corpus/14-deepseek-ascend-stack/raw/DeepEP-Ascend/csrc/buffers/ep.hpp:398`（第 38 章 §3.4）。
   换句话说，「把发起与收尾拆开」这个用法本身就要求「通信跑在单独的
   compute stream 上」，两者是一对。

**常见错误**：以为只要异步发起就能重叠。还必须有第二个 stream 承接重叠的计算。

## E5

**思路**：直接查第 39 章 §3.7 的表。

**答案**：

1. prefill（`Q=4096`）：算力占比 **78.7%**、带宽占比 **8.1%**；
   decode（`Q=256`）：算力占比 **65.3%**、带宽占比 **57.3%**。
2. 因为算力与带宽**两个 roof 都没有接近饱和**，说明上界由第三条流水线给出。
   官方对 MQA logits 的说明是「FIX-pipe bound rather than compute bound,
   saturating the FIX pipe at 99% utilization」
   （`../tilelang-corpus/14-deepseek-ascend-stack/raw/DeepGEMM-Ascend/README.md:142`；第 35 章 §5.5）——每个 `(q,kv)` 对只做一次
   `head_dim` 长的小点积，产出的 L0C 数据立刻要被搬出去，而 logits 本身是个
   稠密大矩阵，于是 `L0C → out` 成了上界（第 36 章 §7.2 在 attention 上
   给出了同一类 bound）。
3. 一般结论：**瓶颈是形状的函数**，而且**只看算力与带宽两个 roof 是不够的**。
   第 39 章 §3.4 与第 28 章 §2.3 的 M2/M3 都在讲这件事。

**常见错误**：看到 prefill 的算力占比 78.7% 就断言「它离算力峰值还差 21%，
再加把劲」。那 21% 不在算力上。

## E6

**思路**：`aic_fixpipe` 是 `KernelProfile` 的一个字段（第 19 章 §8 的表）。

**答案**：

1. 最可能是 **MQA logits**（indexer 打分）这类算子；attention 里也有同一类
   bound（第 36 章 §3.3 的 bound ③）。
2. 应该往「**少搬**」的方向优化：减少 `L0C → out` 的字节（例如减少输出精度、
   让输出更小、或把后续计算融进来），而不是去调 MAD 的形状。
3. 依据是第 35 章 §5.5（MQA logits 是 FIX-pipe bound，99%）与第 19 章 §8.3
   （瓶颈判读决策树：`aic_fixpipe` 高、`aic_mad` 不高时，不要再调 MAD）。

**常见错误**：把 `aic_fixpipe` 当成 Cube 的一部分。FixPipe 是**唯一一条从
L0C 出去的流水线**（`L0C → GM/L1` 或 `L0C → UB`），搬运途中还能做格式转换；
它和 MAD 是两条不同的单元（第 19 章 §2.3）。

## E7

**思路**：直接代公式，注意保留两位小数。

**答案**：

1. `distinct_ranks(32, 6) = 32·(1-(31/32)^6) ≈ 5.55`；
   `distinct_ranks(64, 6) = 64·(1-(63/64)^6) ≈ 5.77`。
   （`code/01-train-step-budget/` 的输出可以直接核对这两行。）
2. `5.77/5.55 − 1 ≈ 4.0%`。
3. 这是「EP 越大越慢」的**第一条**原因：去重率下降、跨设备字节量上升。
   另外两条是：每个 rank 的专家数变少、payload 变小，于是固定开销
   （SQE、doorbell、barrier）被摊得越薄；以及 barrier 成本随 rank 数上升
   （第 38 章 §7.2）。

**常见错误**：把 `distinct_ranks` 当成「实际传输的 rank 数」的精确值。
它是**均匀路由假设下的期望**；真实分布取决于 router 与 EPLB。

## E8

**思路**：逐条对照第 39 章 §4.4 的三条禁令。

**答案**：

* **(a) 错**，违反「不同形状的利用率不能互相外推」。利用率的**分母**是那个形状
   （那台机器）自己的硬件模型（第 35 章 §5.1）；`M=128` 是带宽主导的形状，
   dense GEMM 的 99.8% 对它没有意义。这也正是第 35 章 §8 P10 登记的坑。
* **(b) 错**，违反「不同来源 / 不同口径的数字不能相减或推上限」。
   EP128 的 320 GB/s 是**特定条件下每卡的持续 payload 带宽**
   （16384 tokens/rank、hidden 7168、PoC HDK、含 cache flush），
   它不是「链路带宽上限」。README 自己的说法是「EP≤32 时达到物理 payload
   带宽上限的 90–95%」，那个 90–95% 才是相对上限的说法（第 38 章 §7.4）。
* **(c) 对**（在明确口径的前提下）。这两个数一个来自同一份 `HWDesc`
   （HBM 3500 GB/s），一个是同一台机器上的实测（3463 GB/s），
   同源同机，且 README 自己就说它「nearly saturates the HBM write bandwidth」。
   唯一要注意的是：这张表的字节口径是按 `count_bytes(a, b, d, sqr_sum)` 计的
   （第 35 章 §8 P11）。

**常见错误**：把 (c) 也判成错，理由是「一个是模型常量、一个是实测」。
本条允许比较是因为**同源同机**；§4.4 禁止的是跨来源、跨机器的组合。

## E9

**思路**：从 §7.1 第三档里挑三条，再用 §7.2 的措辞说影响。

**参考答案**（任选三条即可，影响必须与 §7.2 一致）：

* **Bucket 的 reduce-scatter / all-reduce 未实现** → 影响：昇腾上做不了
  bucket 级的集合通信（`../tilelang-corpus/14-deepseek-ascend-stack/raw/DeepEP-Ascend/README.md:80`）。
* **`lb_prefetch_weights` / `lb_reduce_grads` 未实现** → 影响：**动态冗余专家
  （EPLB）暂时不能端到端用**；EPLB 有算法、有 `rebalance_experts` 接口，
  但把权重搬来搬去的通信 kernel 还没有，所以「在线负载均衡」目前只有规划、
  没有搬运（第 38 章 §8.4）。
* **EP 入 graph capture 不支持** → 影响：训练侧的重叠只能靠 DualPipe +
  `defer_epilogue` 这一层；decode 的小 batch 场景要特别小心每次 launch 的
  固定开销（第 38 章 §8.4）。
* **昇腾上的融合 norm-RoPE-attn-RoPE-cast 不支持** → 影响：昇腾侧要自己承担
  这些「小算子」的开销，这也是 TileKernels 在昇腾上更重要的原因之一。
* **DeepSelect 的非 bf16 路径缺失** → 影响：「decode 最后一步选 token」
  在昇腾上要么换精度、要么走别的路径。

**常见错误**：把「不支持」写成「做不到」。第三档的多数条目是「昇腾侧 kernel
还没写」，不是原理上不行（§7.2）。

## E10

**思路**：跑脚本，改 `--topk` 观察比例。

**答案（参考数值，以你机器上的输出为准）**：

1. EP128（`k=6`）：`distinct_ranks ≈ 5.88`，相对 `k` 的比例 `98.1%`。
2. `k=2` 时 EP8 的比例是 `93.8%`、EP128 是 `99.6%`；`k=8` 时 EP8 是 `65.6%`、
   EP128 是 `97.3%`。（以上数值来自脚本输出，可直接核对。）
   （`code/01-train-step-budget/train_step_budget.py --topk 2` 会打印这一行。）
3. 因为 `distinct_ranks` 随 `k` 增长是**次线性**的：`k` 越大，同一批 top-k 里
   「撞到同一个 rank」的机会越多、去重越厉害，所以**在 EP8 时起点更低**
   （比例为 65.6% 而不是 93.8%）；而 EP 一变大，去重的这份优势就消失了
   （比例都逼近 1）。起点低、终点相同，于是 `k` 越大，EP8 → EP128 的
   **相对增幅**越大：`k=2` 是 +6%、`k=6` 是 +33%、`k=8` 是 +48%
   （第 38 章 §1.3 的公式，数值为本书复算）。

**常见错误**：把 `distinct_ranks / k` 当成「通信效率」。它是
「跨卡次数上界被用掉了多少」，不是效率指标。

## E11

**思路**：改 `--m` 看判类翻转。

**答案**：

1. `--m 128`：算术强度 **251.5 FLOP/byte**，平衡点 **247 FLOP/byte**，
   判类 `compute-bound`，但脚本会提醒「落在平衡点附近」。
2. 翻转点在 **`M ≈ 126`** 附近。可以自己验算：
   `AI = 2·M·N/((M+N)·1)`，令它等于 247 解得
   `M = 247·7168/(2·7168−247) ≈ 125.7`。
   所以 `M=64` 是 memory-bound，`M=128` 是 compute-bound。
3. 这与第 28 章 §2.4「多层 roofline：拐点在哪里」是**同一件事**：
   用平衡点反推「从多大规模开始，调 tile 才有意义」。
   第 14 章 §1.2 用 fp16 方阵 GEMM 做过一次同样的计算。

**常见错误**：把翻转点当成一个绝对常数。它随 `N`、随 dtype 的平衡点、
随那台机器的标定值一起变。

## E13

**思路**：第 39 章 §6.1 有完整表。

**答案**：

| 阶段 | 目标 | 判据 |
| --- | --- | --- |
| ① 正确性 | 每个算子与参考实现对得上 | 第 14 章的对拍口径 + 第 18 章 §7.3 的报告清单 |
| ② 单算子利用率 | 每个热点算子贴着它自己的 roof | roofline 判类 + 对应 PIPE 的利用率 |
| ③ 层内融合 | 减少 kernel 数量与重复读写 | 融合前后的 IO 字节数与 kernel 数 |
| ④ 卡间重叠 | 通信不再落在关键路径上 | 通算流水图上的 Wait Time Ratio |
| ⑤ 全局 MFU | 端到端算力利用率稳定 | `C ≈ 6·N·D` 折算的有效 TFLOPs ÷ 峰值 |

**为什么 ③ 在 ④ 之前**：融合会改变 kernel 的数量与形状，从而改变通信与计算的
配比。第 35 章 §5.6 的 MegaMoE 就是「先融合、再谈重叠」的极端版本——
它把 dispatch、两个 grouped GEMM、SwiGLU、combine 融成一个 kernel 之后，
「重叠」这件事变成了同一个 kernel 内部的进度阶段交错，而不是两次 launch 的
调度问题。

**常见错误**：把 ② 与 ⑤ 混为一谈。单算子利用率高，端到端 MFU 仍可能很低
（通信没重叠、或者 kernel 太碎）；反过来也一样。

## E14

**思路**：这题没有唯一答案，评分看四件事是否都写清。

**参考答案（以 `lb_prefetch_weights` 为例）**：

1. **路径**：属于**路径一（写算子）**。理由：接口已经对齐
   （`EPBuffer.lb_prefetch_weights` 与 NV 版 DeepEP 同名同参），缺的是
   **昇腾侧的通信 kernel**——源码里那两处 `EP_HOST_UNREACHABLE`
   （`../tilelang-corpus/14-deepseek-ascend-stack/raw/DeepEP-Ascend/csrc/buffers/ep.hpp:79,85`）就是它现在的状态。
   通信 kernel 在昇腾上要直接操作 URMA 队列，所以它更接近「写一个
   Ascend C kernel」而不是「改编译器」。
2. **怎么确认值得做**：用第 39 章 §5 的顺序——先判类（这一步不改变任何算子的
   算术强度，所以它只会影响通信占比），再看通算流水图上的 Wait Time Ratio；
   只有当「负载不均导致的等待」真的出现在你的关键路径上时才值得做。
   EPLB 的价值取决于你的专家负载分布，这是**用你的数据才能回答的**问题。
3. **收益属于哪一层**：**数学层**。它改变的是「把权重搬到哪里、搬多少」这件事
   本身（第 37 章那句「算法决定上限、硬件决定常数」里的前者），
   不是某个 kernel 的常数项。
4. **要跑的门**：第 31 章 §2.3 的四道门——门 1 格式与 lint、
   门 2 本地测试、门 3 上游 CI（昇腾侧有独立的 `ascend` job）、
   门 4（按需）性能回归；另外昇腾适配器仓库有自己的 PR 模板要求
   （第 31 章 §7.2）。

**可以在纸上完成，但必须标出「需要真机才能确认」的部分**：
kernel 的实现与对拍、µs 级的 launch 开销、以及「加上搬运之后端到端是否变快」，
这些都需要多卡昇腾环境。

**常见错误**：直接写成「这是个 TODO，我来实现」。缺少前三步的判断，
就会做出一个「实现正确但没人需要」的 PR——这正是第 31 章反复强调
「先确认它是不是瓶颈」的原因。
