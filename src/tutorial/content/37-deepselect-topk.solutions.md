## E1

**思路**：§1.1 给了两个位置的定位，§1.3 给了两笔账。

**参考答案**

1. 两个位置：
   * **DSA 的 Lightning Indexer**：先用轻量打分给每个 context token 打分，
     再用 TopK 选出最相关的 `topk` 个**上下文位置**（后续 MLA 只读这些位置的 KV）。
   * **采样器（Sampler）**：从整张词表的 logits 里选出 `topk` 个**候选 token**，
     再按权重采样。
2. 共同形状：`k` 小（≤ 4096，主要 512）、`N` 大（context 可到百万，词表约 128K）；
   dtype 不同（Indexer 是 bf16，Sampler 是 fp32）。
3. 两笔账：
   * 「读一遍 `N`」是**物理下限**——没有任何算法能不读某个元素就断定它进不了 top-k；
   * 「与 `N` 同阶的选择/排序」是**可以省掉的**——`torch.topk` 有这一趟，
     DeepSelect 把它挪到了大小为 `O(k+B+B2)` 的候选集合上。

**常见错误**：把「排序」说成「不可避免」。DeepSelect 的全部意义就是**不排序**，
只有最后输出 `sorted_index` 时才对 `k` 个元素排一次（§5.2）。

## E2

**思路**：§2.2 逐行读了伪代码。

**参考答案**

1. ① 扫描（对每个块都做）→ ② 筛选（对每个元素做）→ ③ 压缩
   （触发条件：`len(topk_candidate) >= k + B2`）。扫描结束后再做最后一次压缩。
2. 因为压缩本身有成本，而一次压缩只能「留下 `k` 个」。若触发线是 `k`，
   缓冲区刚超过 `k` 就压，**压缩次数会急剧上升**（`R` 变大），
   而 §3.6 的 `E[W] = A + kR` 里 `kR` 这一项会被放大。
   `B2` 是留给缓冲区的松弛量，让「多攒一点再一次性处理」。
3. 阈值要表示「当前第 `k` 大的值」：压缩后缓冲区里正好是当前见过的最大 `k` 个，
   所以**它们的最小值**就是第 `k` 大。若改成取最大值，阈值会被抬到「第 1 大」，
   于是后续几乎所有元素都被 `>` 过滤掉，**结果会错**（漏掉真正的 top-k）。

**常见错误**：认为触发线是 `k` 是笔误。它不是——`k+B2` 是算法的一部分，
`B2` 与 `k` 在复杂度界里也是两个独立的量。

## E3

**思路**：§2.3 给了机制，`code/02` 给了数据。

**参考答案**

1. **升序输入 + 顺序扫描**（或等价的 `staircase`：每块一个常数、随块号递增）。
   退化机制：头两块把阈值定在一个很小的值上，之后的每一块的值**全都大于阈值**，
   于是整块被接受 → 每块触发一次压缩 → `A` 涨到 `N`。
   实测（`N=262144, k=512, B=B2=1024`）：`A = 262,144`、`W = 392,704 ≈ 1.5N`。
2. `descending`（大值在前）时，顺序扫描第一块就拿到大值，阈值立刻涨到位，
   后面全是过滤，所以 `A` 只有 `k+B2` 量级：实测 `A = 2,048`、`W = 2,560`，
   比随机顺序（`W = 11,776`）还省。
3. **最后一列 `correct`**。它全是 `True`，说明两种顺序给出的 top-k 都对——
   随机化只改变代价（`A`/`R`/`W`），不改变结果。这一列重要，是因为它把「性能问题」
   与「正确性问题」分开：如果这一列出现 `False`，那问题在算法/实现，不在随机化。

**常见错误**：说「随机化保证正确性」。报告的口径是「避免极端输入下的性能退化」
（`DeepSelect-deep-dive.zh.md:43`）。

## E4（手算复杂度）

**思路**：直接用 §3.1 的定义与 §3.6 的结论。

**参考答案**

1. `m = ceil(262144 / 1024) = 256`。
2. `L = k + B + B2 = 512 + 1024 + 1024 = 2560`。
3. `H_256 ≈ ln(256) + 0.5772 = 5.5452 + 0.5772 = 6.12`（两位小数）。
4. `(1 + k/B2) = 1.5`；界 `= 1.5 × 2560 × 6.12 ≈ 23,500`（精确求和 `H_256` 得
   23,517，`code/03` 的 Table 1 就是这个数）。
5. `E[W]/N ≈ 23,500 / 262,144 ≈ 0.0897`，即**额外工作量不到「读一遍输入」的 9%**。

**常见错误**：用 `log2` 算 `H_m` 的近似（应该是自然对数 `ln`）；
或者忘记 `(1 + k/B2)` 这个因子。

## E5

**思路**：§3.1 的符号表 + §3.2–§3.4 的推导。

**参考答案**

1. `C_i` = 开始处理第 `i` 个块时的候选缓冲区；`A_i` = 处理该块时**新增**的元素数；
   `U_i` = 前 `i` 个已处理块的集合；`T_i` = `U_i` 中前 `L` 大的元素。
   `T_i` 用 `L` 而不是 `k`：因为「被加入的元素」的排名上界是
   `|C_i| + |B_i| < (k+B2) + B = L`（§3.2），所以用 `L` 才能兜住它；用 `k` 会漏。
2. 依赖两个事实：
   * **块边界**：一个块最多 `B` 个元素（来自扫描的块划分）；
   * **循环不变量 `|C_i| < k+B2`**（来自「达到 `k+B2` 就压缩」）。
   再加上「历史落选元素都不大于当前阈值」，所以「比被加元素大的历史元素」只能来自
   `C_i ∪ B_i`。
3. `1/i` 来自**随机块序**：在给定 `U_i` 的条件下，第 `i` 个块在 `U_i` 的 `i` 个块里
   均匀分布，所以期望贡献是「把 `U_i` 的贡献取平均」，即除以 `i`。
   换成顺序扫描就**不成立**——「谁是最后一个」不再均匀（是地址最大的那个），
   `code/02` 的退化就是这一步失效的直接后果。

**常见错误**：把 `1/i` 说成「因为块大小是 `1/i`」。`1/i` 与块大小无关，
它是**均匀性**的产物。

## E6

**思路**：§4.2、§4.3 给了完整解释。

**参考答案**

1. `hit_mask` 的第 `i` 位 = 「本线程本轮的第 `i` 个元素是否大于阈值」。
   它由三条 PTX 指令生成：`set.gtu.s32.bf16x2`（一次比较两个 bf16）、
   `prmt.b32`（挑位/取字节）、`dp4a.s32.s32`（把 4 个命中压成一个 nibble）。
   （`common_parts.cuh:1413-1428`。）
2. `__ffs(mask)` 返回最低的 1 的下标；`mask &= mask - 1u` 把最低的 1 清掉。
   重复「取下一位 + 清掉它」，就能按从低到高的顺序遍历所有为 1 的位——也就是所有命中。
3. 循环体执行次数 = `popcount(mask)` = 本轮的命中数。命中越稀疏（阈值越高），
   循环体越少、写回越少，所以收益越大。
4. 因为最低的那个命中元素被**提前单独读出并处理**（预取 `common_parts.cuh:1449-1452`，
   写回 `:1471-1475`）：
   让它的 shared memory 读延迟和后面的前缀和/计数交换重叠。第一行先把它清掉，
   后面的循环就只处理剩下的位。

**常见错误**：把 `mask &= mask - 1u` 说成「右移一位」或「清最高位」。
它是**清最低的 1**；`mask - 1u` 的借位把所有更低位的 0 变 1、最低的 1 变 0。

## E7

**思路**：§4.8 的表就是答案。

**参考答案**

| 瓶颈 | 技巧 | 为什么 |
| --- | --- | --- |
| (a) 两遍扫描 | (2) `hit_mask` + `__ffs` 枚举 | 只枚举命中的位，第二遍不再扫过未命中的元素 |
| (b) mask 生成指令多 | (3) `set.bf16x2` + `prmt` + `dp4a` | 4 个元素一组、5 条指令出 4 个 bit |
| (c) 整数加法抢端口 | (4) 浮点加法替整数加法 | 把地址自增搬到浮点流水线，与比较/位运算不冲突 |
| (d) 写回偏移关键路径长 | (5) ballot 版 warp 前缀和 | 命中数 ≤ 16，5 次 ballot 比 5 步 shuffle 扫描短 |
| (e) 直方图吃指令数 | (6) `red.shared.add` + `mad` 算桶地址 | 一次循环处理两个元素、两条原子加 |
| (f) batch 太小 | (1) Threadblock Cluster | 一条序列切到多个 SM，CTA0 归并，减少空闲 SM 与 wave quantization |

**常见错误**：把 (b) 配成 (5)。(5) 解决的是「算写回偏移」的延迟，不是「生成 mask」
的指令数——虽然两者都在 warp 层面，但是两件事（§4.5 的插入语专门说明了这一点）。

## E8

**思路**：§4.4。

**参考答案**

1. 前提是 `0 ≤ x, y ≤ 2^22`。此时位模式的符号位与指数位全为 0，作为 float32 读出来是
   **次正规数**，其尾数恰好就是整数本身；两个 `≤2^22` 的整数相加 `≤ 2^23`，
   仍在次正规范围内，浮点加法不会规格化，所以**进位不会串到指数位**，
   结果位模式与整数加法一致。
2. `0f00000008` 是整数 `8` 的 32 位位模式（十六进制 `0x00000008`）；
   `%0` 是 shared memory 指针的整数地址。这一行等价于 `dst_ptr += 8`（`add.u32`）。
   （`common_parts.cuh:1041,1086`。）
3. 不成立。`x = 2^24` 已经进入规格化范围，位模式的指数位不再是 0；
   浮点加法会把进位加到指数位，结果位模式变成另一个数（地址算错）。
4. 因为这个技巧压的是 **CUDA 上「整数加法与比较/位运算抢执行端口」**这一个具体资源。
   昇腾的向量/标量指令组织与流水不同，没有这条动机；昇腾侧强调相反方向
   （减少同步、平衡 Cube/Vector）。

**常见错误**：把条件说成「x、y 是 32 位无符号整数即可」。条件不是位宽，
而是**数值范围**（`≤ 2^22`）。

## E9

**思路**：§2.5 与 §5.2。

**参考答案**

1. `len(topk_candidate) ≤ k + B2 + B`：`k` 是压缩后保留的目标数，`B2` 是触发压缩的
   松弛量（触发线 `k+B2`），`B` 是两次压缩之间最多再扫进来的元素数。
2. `kCandidateCapacity = kTopkCapacity + kBlockSize + kFilteredCapacity`
   （`.../DeepSelect/csrc/ascend_kernels/config.h:195`）——右边正是 `k+B+B2`。
3. `k+B+B2 = 512 + 16384 + 4096 = 20,992`。它被存成三份等长的 part（value /
   index_low / index_high），每份 `(20992+256)×2 B ≈ 41.5 KB`，三份约 124.5 KB，
   在代码声明的 UB 预算 `248 KB` 以内（`config.h:19,196-203,238`）。
4. 意味着候选可以**全程留在片上**：不需要为它做全局内存的读写（即 no extra HBM
   round trips）。如果放不进片上，每一次「筛选 → 压缩」都要经全局内存，
   额外带宽就与候选量成正比——那时 `O(k log(N/k))` 就不再是「小量」了。

**常见错误**：把 `B2` 当成「缓冲区大小」而不是「松弛量」；或漏掉三份 part。

## E10

**思路**：§5.4 与 §5.5。

**参考答案**

1. **TileLang**：形状固定、逐行独立的融合逐元素/归一化算子，收益来自「少搬字节」，
   能用 `(flops, bytes)` 说清，第 13 章有现成写法，两个后端都能覆盖。
2. **手写**：收益来自 warp 级归约 + 位级枚举 + 前缀和这类**细粒度线程协作**，
   tile 抽象里没有对应的表达方式（判据表第一、二行）。
3. **TileLang**：需要双后端，收益是规则的 tiling + epilogue 融合；
   一份代码两个 target 的成本远低于写两份（判据表第三行；对照第 33 章）。
4. **手写（在 TileLang 版之上）**：先用 TileLang 得到一个正确、接近上限的版本，
   再定点替换最热的 kernel。这是判据表最后一行。

DeepSelect 属于「手写」，至少两条判据：
* 收益来自**指令级/端口级**的技巧（mask、浮点替整数加法、census 用浮点累加）——
  这些写不进 `(flops, bytes)`；
* 需要用 DSL 未暴露的机制（Threadblock Cluster / DSM）与 PTX；
  另外它的核心数据（一行百万元素）**放不进片上**，而 `T.tile.topk` 要求静态形状
  并且是排序式的。

**常见错误**：用「性能要求高」当理由。判据不是「快不快」，而是
**收益能不能写成「少搬字节/少做乘加」**——能就 TileLang，只能写成「少发几条指令」
就手写。

## E11

**思路**：§5.2 的「需要与作者确认的偏差」。

**参考答案**

1. 种子来自输入**前 8 个字节**的哈希，再与行长 `valid_len` 异或：
   `permutation_seed = input_hash ^ valid_len`。
2. **不满足**。报告要求排列「independent of x」；这里排列显然依赖于 `x` 的前 8 字节。
   所以 §3 的期望分析不能原样套用到这个实现上（工程上，输入是模型数据而非对抗输入，
   风险很小，但严格来说是一个假设偏差）。
3. 好处：每一行得到**不同的**处理顺序，又不需要维护/传递随机数状态（种子可由行数据
   导出），且对同一输入可复现（便于调试）。
   隐患：**均匀性**与**独立性**都不严格成立——`TopkPermGenerator` 用的是
   `(value*65537+seed) % size` 这类模运算（`config.h:83-86`），是伪随机而非均匀随机；
   若输入分布恰好与这个映射相互作用，理论界可能不成立。
4. 按源码注释（`config.h:39-42`），`TopkPermGenerator` 处理三种情况：
   （a）短输入（页数不超过 `warmup_pages`）**按顺序**扫；
   （b）长输入时，**整页按随机顺序访问**；
   （c）物理尾部的最后一"页"会被对齐到 128 元素边界切开，**后一段放在 warmup 的末尾**，
   **前一段放到最后访问**——目的是让页起点保持 128 对齐、且不越界读
   （`config.h:62-87`）。
   影响的不变量：因为顺序不是**全体页**的均匀排列（有 warmup 与尾部三处的特判），
   §3 的期望分析严格说只覆盖「随机访问的整页」那部分；特判的部分是有界且确定的，
   需要单独记账（预热阶段的 `A_i` 上界是 `warmup_pages × page_size`）。

**常见错误**：认为「种子来自输入」等价于「顺序扫描」。不是——它仍然是打乱的，
只是这份打乱不是与输入独立的均匀随机。

## E12

**思路**：跑一次就知道了；关键是解释为什么。

**参考答案**

1. `staircase` 行（`k=512`）：
   * `sequential`：`A = 262,144`、`R = 255`、`W = 392,704`（`W/N ≈ 1.498`）；
   * `random`：`A = 6,144`、`R = 5`、`W = 8,704`（`W/N ≈ 0.033`）。
2. 因为 `staircase` 的构造就是「每 `B` 个元素取一个常数、常数随块号递增」，
   而 `ascending` 是「连续递增」——两者都满足「后面的块的值整体大于前面的块」，
   所以顺序扫描的退化机制完全一样。
3. 把 `k` 改成 1024（`--k 1024`）：随机顺序下 `W/N` 从 0.033 涨到约 0.043
   （`W = 11,264`），变大了。原因见 §3.7：界 ≈ `(1+k/B2)(k+B+B2)·H_m`，
   在 `B2` 固定时它大致按 `k` 增长（`k=256` 时约 0.028，`k=512` 时 0.033，
   `k=1024` 时 0.043）。
4. 真实 kernel 上不能数「元素个数」当时间，应当看：
   `tests/test.py` 口径的**有效带宽**（(输入+输出字节)/时间）与**相对 `torch.topk`
   的倍数**；再配合 profiler（CUDA 用 Nsight，昇腾用 msProf，见第 12、19 章）
   看瓶颈在哪条流水。判据是「离只读一遍有多近」，不是「`W` 是多少」。

**常见错误**：以为 `W/N` 应该随 `k` 减小。界大致正比于 `k`，所以 `k` 变大、
相对开销变大。

## E13

**思路**：§6.1 与 §6.2。

**参考答案**

1. 定义式：`total_size = 输入字节 + 输出 value 字节 + 输出 index 字节`，
   有效带宽 `= total_size / time`（`tests/test.py:150-170`）。
2. 因为「有效带宽」的分子是**这个算子实际搬了多少字节**。GEMM 的算术强度高、
   分子小分母大；TopK 几乎没有浮点计算、分子就是输入规模。两个算子的
   「字节/时间」不是同一个物理量，不能互相比较（§6.1 第 3 点）。
3. 因为加速比是**两个实现之比**：`torch.topk` 在 bf16 + 超长行 + 小 `k` 时相对最弱
   （分母小 → 倍数接近 20×）；在 fp32 + 固定 128K 词表时相对更好
   （分母大 → 倍数接近 2×）。所以「2～20×」对应的是不同形状。
4. 不是算法有问题。两个原因：
   * **活跃 SM 太少**：行数少，一个（或几个）CTA 喂不满 GPU；
   * **wave quantization**：最后一个 wave 里活跃 CTA 很少，其余 SM 空转。
   仓库为此专门做了 Threadblock Cluster 版本，触发条件包含 `batch_size <= 6`
   （`csrc/api.cpp:156`）。

**常见错误**：把「有效带宽低」直接读成「实现差」。在小 batch 下，
低带宽是**并行度**问题，不是单 CTA 的效率问题。
