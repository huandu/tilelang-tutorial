## E1

**思路**：第 2.1–2.4 节的三张表就是答案的全部来源；关键是理解“有效位”而不是背数字。

**参考答案**

1.

| 格式 | 符号/指数/尾数 | `p` | `u = 2^-p` |
| --- | --- | --- | --- |
| fp16 | 1/5/10 | 11 | 4.883e-04 |
| bf16 | 1/8/7 | 8 | 3.906e-03 |
| fp8 e4m3 | 1/4/3 | 4 | 6.250e-02 |
| fp8 e5m2 | 1/5/2 | 3 | 1.250e-01 |
| fp4 e2m1 | 1/2/1 | 2 | 2.500e-01 |

2. bf16 把 fp32 的 8 位指数原样保留，所以**溢出/下溢行为与 fp32 一致**：训练里
   梯度的量级跨度很大，fp16 容易下溢；代价是尾数只剩 7 位，相对精度比 fp16 低 8 倍。
   浮点数里指数位管范围、尾数位管精度，16 位预算下只能二选一。
3. `u_int = 1/(2·qmax)`：int8 是 `1/(2·127) = 3.937e-3`，与 bf16（3.906e-3）
   同级；int4 是 `1/(2·7) = 7.143e-2`，与 fp8 e4m3（6.25e-2）同级。
4. **主要由粒度决定。** 证据：`code/02` 里 per-tensor int8 的相对 L2 是 `4.95e-2`
   （比 3.9e-3 的上界大一个数量级），而 per-channel int8 降到 `7.67e-3`，
   位宽完全没变。

**常见错误**：把 `p` 数成“尾数位数”（fp16 是 10 而不是 11），
有效位数含隐含的前导 1，所以是 `1 + 尾数位`。

## E2

**思路**：e4m3 的位模式有限（只有 256 个），范围与特殊值的设计是硬性取舍；
跨平台差异来自“谁来选变体”。

**参考答案**

1. e4m3 只有 4 位指数，如果像 IEEE 那样把指数全 1 划给 inf/NaN，
   就只剩 14 个指数档位可用，最大有限值会小得没法用。所以 OCP 的规定是
   **牺牲 inf**：指数全 1 仍是有限值（最大值 448 = 1.75×2^8），
   NaN 只留 `0x7f`/`0xff`。
   对量化流程的要求：**必须保证 `|x/scale| <= 448`**，否则会直接变成 NaN
   （不是像 fp16 那样变成 inf）。这就是 `ceil_to_ue8m0(amax/448)` 必须**向上**取整
   的原因。
2. 前向的激活与权重经过归一化，量级集中，需要的是相对精度 → e4m3；
   反向的梯度动态范围大（有极小值也有离群值），需要范围 → e5m2。
3. ROCm（非 gfx950）的对应格式是 `float8_e4m3fnuz`，**位模式定义不同**
   （FNUZ 没有负零、NaN 编码也不同）。硬编码 `e4m3fn` 会被后端当作合法输入接受，
   但数值解释不一样，结果是错的而不报错。所以是静默错误。
   正确做法是 `determine_fp8_type()` / `determine_torch_fp8_type()`。
4. 在**逐位比较**或 `atol=0` 的对拍里：`-0.0` 与 `+0.0` 的位模式不同，
   会被判成不相等。锁定版本提供了 `fp8_remove_negative_zeros_`
   （`tilelang/utils/tensor.py:25-29`）。

**常见错误**：以为“e4m3 溢出会变成 inf”。它是 NaN，而且 `0x7f` 正好是
最容易出现的编码，会让误差看起来“突然爆掉”而不是“饱和”。

## E3

**思路**：三个要素分别对应“多少元素共享”“scale 是什么”“怎么存”。

**参考答案**

1. 都是 **32**。PTX 在 `9.7.18.10.7.2` 里规定 `.kind::mxf8f6f4` 的
   scale_A 是“每个 A 的行按 32 个 K 元素分块”
   （`../tilelang-corpus/05-nvidia-backend/raw/nvidia-ptx-isa.md:32136-32150`）；
   CATLASS 是 `constexpr uint32_t MX_SCALE_GROUP_NUM = 32;`
   （`catlass/include/catlass/catlass.hpp:48`）。
2. 值域 `2^-127 .. 2^127`（编码 0..254，255 保留给 NaN）。
   它的尾数位是 0，**没有编码可以表示 0**，也没有负数。
   因此“整块全零”不能靠 scale 表达，只能选一个约定的最小指数兜底；
   锁定版本在打包时的填充值是 `127`（即 `2^0 = 1`），而不是 0
   （`examples/blockscaled_gemm_sm100/gemm_mxfp8_blockscaled_1d1d.py:566`）。
3. 因为 scale 是 `2^k`，`x / 2^k` 只是把 `x` 的指数减 `k`，尾数不变。
   在 fp32 里只要指数不越界，这个操作是**精确**的（没有舍入）。
4. (a) 合法，因为 32 是硬件最小粒度，**更粗是允许的**（同一个字节服务 4 个连续的
   K32 原子）；(b) `sf_load_period = sf_granularity_k * 4 // block_K`，
   用 128 时一个 word 覆盖 `4 × 128 = 512` 个 K 元素，`block_K = 128` 时正好是
   4 次迭代搬一次；(c) 昇腾侧**不能**：`tilelang/ascend/language/gemm_op.py:155-156`
   把 `sf_a_granularity_k` / `sf_b_granularity_k` 写死为 32，
   CATLASS 的模板也只参数化了“L1 上驻留几个条带”（`L1_SCALE_FACTOR_K`），
   没有暴露粒度。

**常见错误**：把 32 当成“TileLang 的限制”。32 是 MX 的规范粒度；
128 是 TileLang 在 SM100 示例里主动做的加粗。

## E4

**思路**：粒度决定 scale 的数量与每个 scale 覆盖的数值范围，误差上界是
`absmax_of_its_group / (2 qmax)`。

**参考答案**

1.

| 方案 | scale 个数 | 相对权重（fp32 scale）的开销 |
| --- | --- | --- |
| per-tensor | 1 | 可忽略 |
| per-channel（4096 行） | 4096 | 4096×4 B / (4096×4096×1 B) = 0.1% |
| per-group-64（沿 K） | 4096 × 64 = 262144 | 262144×4 B / 16 MiB = 6.25% |

   （权重组按 int8 的 1 字节算；如果权重是 int4，两项开销各翻倍。）
2. 排序是 per-group-64 < per-channel < per-tensor（误差从小到大）。
   粒度越细，每组的 absmax 越接近该组数据的真实量级，量化步长越小。
3. 用 `python3 code/02-quant-dequant/quant_dequant.py` 复算，实测
   per-tensor `4.951e-02`、per-channel `7.674e-03`。
   per-tensor **大于**理论上界的原因：上界是相对 **absmax** 的
   （`absmax/2/qmax ≈ 3.9e-3`），而相对 L2 是全体元素的均方；
   这份数据里 per-tensor absmax=86.5、per-row absmax 中位数=3.44，差 25 倍，
   于是绝大多数元素的实际误差远大于“相对 absmax 的上界”。
4. int4 的 `qmax = 7`，上界变成 `7.1e-2`，三种粒度的实测分别约为
   `1.08e-1`（group-64，见脚本输出）、以及更大的 per-channel / per-tensor。
   要落到 `1e-2` 以内，需要**更细的粒度**（例如 group-16 或 group-32
   再配合 per-channel 的 scale 组合），单纯换位宽做不到。

**常见错误**：把“per-channel 更好”解释成“per-channel 用了更多比特”。
位宽没变，变的是 absmax 的适用范围。

## E5

**思路**：两类误差的来源、量级、随 K 的行为都不同，要能分开说。

**参考答案**

1. **输入舍入误差**来自“把数据存成低精度”，与 K 无关（上界恒为 `u`，
   均方根按 `1/√K` 缩小）；**累加误差**来自乘积累加时的舍入，与输入精度无关，
   取决于累加器类型和归约顺序。
   证据：`code/03` 实验 A（fp16 的“对量化值”误差是 5.9e-9，说明输入量化误差
   与累加误差可以差 4 个数量级）与实验 C（同一输入换累加器，1.24e-4 → 1.24e-9）。
2. `u/√K` 模型假设“每个元素的相对误差上界是 u”。fp4 e2m1 的值只有
   `{0, 0.5, 1, 1.5, 2, 3, 4, 6}`，相邻档位的相对间距在 `[1,2)` 里是 50%、
   在 `[0.5,1)` 里是 100%。**小数值的相对误差远超 u**，所以“相对上界”这个
   前提不成立，模型失效（实测是预算的 2.58 倍）。
3. 三个数字：fp16 顺序累加 `1.238e-04`、32 段 fp16 + fp32 汇总 `2.063e-05`、
   fp32 累加 `1.243e-09`。split-K 的收益来自“每段的舍入误差只与该段长度有关”，
   段长从 K 变成 K/32，段内误差随之减小，而段间用 fp32 连接不再引入新的放大。
   与“直接换 fp32 累加器”的区别：后者精度更高但要全程付出 fp32 的代价
   （寄存器/带宽），split-K 是“用并行度换精度”，还能顺带提高 SM 利用率。
4. `src/op/tcgen5_meta.h:79-82` 里，f8f6f4 家族的判据是
   `(c_dtype.is_float() && c_dtype.bits() == 32) || (c_dtype.is_float16() && c_dtype.bits() == 16)`，
   **fp16 累加器是被显式允许的**，所以能通过编译。它错在数值上而不在类型上：
   累加器的精度直接决定第 2.5 节实验 C 那一档误差。

**常见错误**：把“fp8 的结果不精确”一概归为“fp8 精度低”。
累加器选择造成的误差可以比输入精度造成的误差大 4 个数量级。

## E6

**思路**：把公式代进去算，再解释每一步在做什么。

**参考答案**

1. `k_iters = 4096/128 = 32`；`sf_load_period = 128*4/128 = 4`；
   `sf_k_groups = ceil(ceil(4096/128)/4) = ceil(32/4) = 8`。
2. `SFA` 的长度是 `8 * M`。它是 `uint32` 因为一个 word 要装 4 个 E8M0 字节
   （4 个连续的 scale），用 `uint8` 就无法表达“一次搬一组”的语义，
   也没法直接喂给 `tcgen05.cp`。
3. 这个条件表示“每 4 次 K 迭代才需要搬一个新的 scale word”，
   一个 word 覆盖 `4 × 128 = 512` 个 K 元素，而每次迭代消费 128 个，
   所以正好 4 次迭代用同一个 word。每次都搬在功能上仍然正确（同一个值重复搬），
   但会让 TMA 的请求数变成 4 倍，还会打乱 SF 的流水对齐。
4. `pack` 的表达式是
   `packed = words[:,0::4] | (words[:,1::4]<<8) | (words[:,2::4]<<16) | (words[:,3::4]<<24)`，
   然后 `packed.T.contiguous().reshape(-1)`。
   最后一步把形状从 `[MN, groups]` 转置成 `[groups, MN]` 再展平，得到
   **group-major** 的顺序：`SFA[g*M + m]`，先按“第几组 scale”，再按行号。
   不转置就是行主序，见 E10。

**常见错误**：把 `sf_k_groups` 算成 `K / sf_granularity_k / 4` 的整数除法而漏掉
`ceil`。K 不是 512 的整数倍时（例如 K=4000）会少算一组。

## E7

**思路**：这是一个“位运算做类型转换”的经典技巧，动手验证比推公式快。

**参考答案**

1. 第一行取出第 `pos` 个 4 位组（`0` 或 `1`），得到 `[0,15]` 的无符号值；
   第二行把它左移 4 位放到 `int8` 的高 4 位，此时低位是 0、符号位由原值决定；
   第三行做**算术**右移 4 位，低 4 位补回符号位，得到正确的有符号值。
   不能直接 `val >> (pos*4)`：那样得到的是无符号值，`-1`（即位模式 `0xF`）
   会被解释成 `15`。
2. `val = 0xF0`：`pos = 0` 时 `i4 = 0x00`，结果 `0`；
   `pos = 1` 时 `i4 = 0x0F`，左移后是 `0xF0`，按 `int8` 解释是 `-16`，
   算术右移 4 位得 `-1`。
3. `pack_int4` **没有**处理符号位，它只是把两个 `int8` 的低 4 位拼起来
   （`& 0x0F`）。负数在 int8 里的低 4 位正好是它的 4 位补码，所以解码端
   靠第 2 问的算术右移还原。
4. 因为整条路径在整数域完成：int4 × int4 的乘积最大 64，int32 累加不会溢出，
   没有任何舍入。fp8 路径有输入舍入与（可能的）累加舍入，所以只能给容差。

**常见错误**：把“解包”写成逻辑右移（`>>>` 或 numpy 里对 uint8 右移），
负权重会整体偏移 16。

## E8

**思路**：`% 4` 与“4 个字节一包”是同一件事的两面。

**参考答案**

1. `% 4` 表示“在一个 32 位 TMEM 单元格的 4 个字节里选第几个”。
   是 4 而不是 8/16，因为 E8M0 是 8 位、单元格是 32 位，`32/8 = 4`。
   这个 4 同时被 PTX 写进了指令描述符的字段宽度（2 位）。
2. `k_start = 256`、`gran = 128`：`(256 + ki*32) // 128` 在 `ki=0..3` 时都是 `2`
   （`256/128=2`、`288/128=2`、`320/128=2`、`352/128=2`），
   所以 `runtime_sf_a_id` 都是 `2`。
   也就是说**一个 scale 字节服务 4 个连续的 K32 原子（共 128 个 K 元素）**，
   这正是 `sf_a_granularity_k = 128` 的含义。
3. 生产端按 128 打包、消费端按 32 解码时，消费端会用同一个字节去覆盖 32 个元素，
   四个原子各自读到不同的字节，但那些字节其实是别段的 scale。
   `code/05` 的第 3 行就是这个错误：相对 L2 = `2.773e+00`。
4. 是同一个 4，但讲的是两件事：`% 4` 是**选**哪个字节（索引），
   “128 word → 4 个 TMEM 列”是**写**入时的搬运形状。
   它们的共同来源是“TMEM 单元格 32 位 = 4 个 E8M0 字节”；
   搬运时按 4 列铺开，正是为了让 `% 4` 的索引能直接命中。

**常见错误**：把 `sf_a_granularity_k` 理解成“一个 word 覆盖的 K 元素数”。
一个 word 覆盖 `4 × granularity`，两者差 4 倍。

## E9

**思路**：先定位反量化在数据流里的位置，再判断它对 scale 粒度的要求。

**参考答案**

1. **位置 C（epilogue）**：int8 在 L0C 里以 int32 累加，搬到 UB 之后
   才乘 `scale_ub` 并 cast 到 fp16/bf16。
   合法的前提是 `scale` **与 K 无关**（per-tensor 或 per-channel）：
   累加完之后再乘，等于把 `Σ_k a_k b_k` 整体缩放，与逐项缩放等价。
2. 不能用。per-K-block 的 scale 意味着每一项乘积要乘自己那一块的 scale，
   而 `Σ_k a_k b_k s_{block(k)}` **不能**写成 `(Σ_k a_k b_k) · s`。
   这时必须回到图 4 的位置 A（搬入时反量化）或位置 B（块缩放 MMA）。
3. 判据是 `torch.testing.assert_close(C.cpu(), ref_C.cpu(), rtol=1e-2, atol=1e-2)`
   （`:116`）。合理：误差只来自“权重与激活的量化”这一项，
   而 per-channel int8 的量化误差量级是 `1e-3 ~ 1e-2`（见第 5.3 节的基线表），
   `1e-2` 的容差正好覆盖它，同时又能抓住量级错误。
4. 差别在**粒度**：昇腾 MX 路径的粒度固定 32 且沿 K，scale 是 1 字节的 E8M0，
   由 Cube 在 L1→L0 阶段消费；这份示例的 scale 是 fp32、与 K 无关、
   在 epilogue 消费。前者的场景是“权重和激活都是 MX 格式、追求带宽”；
   后者是“W8A8 的 per-channel 量化、实现最简单”。

**常见错误**：认为“epilogue 反量化”是通用方案。
它只在 scale 与 K 无关时成立；一旦 scale 沿 K 分块，误差会随 K 的位置累积。

## E10

**思路**：直接跑脚本，观察 `sf_k_groups` 如何随 K 变化，再想清楚“什么时候两种
索引恰好等价”。

**参考答案**

1. 默认 `--k 1024`：第 2 行（行主序）的相对 L2 = `2.469e+00`；
   末尾那句的取值是 `True`。
2. `--k 512`：第 2 行的相对 L2 变成 `0.000e+00`，即**检测不出错误**。
   因为 `sf_k_groups = ceil(ceil(512/128)/4) = ceil(4/4) = 1`，
   只有一个 word 组，`packed.reshape(1, mn).T` 与 `packed.reshape(mn, 1)`
   是同一个数组，两种索引完全等价。
3. `--k 2048`：`sf_k_groups = 4`，第 2 行变成 `8.998e-01`。
   K 越大、组数越多，两种索引的差异越明显（差异的大小还取决于各组 scale 的
   差异程度，所以 K=2048 的数值比 K=1024 小并不奇怪。关键是“非零”）。
4. 思路：在 `unpack_sf_u32_1d` 里加一个前置检查，或在校验函数里判断
   `sf_k_blocks <= 4`。关键代码：

   ```python
   if sf_k_blocks <= 4:
       print("警告：只有 1 个 word 组，group-major 与 row-major 等价，"
             "这个用例无法检测出 scale 布局错误；请把 K 增大到 > 4*gran。")
   ```

**常见错误**：把 K=512 的 `0.000e+00` 当成“布局没问题”的证据。
它恰恰说明**这个用例没有鉴别力**，是测试设计的缺陷而不是实现正确的证明。

## E11

**思路**：`u` 的定义方式会整体平移“实测 / 预算”这一列，但这不影响结论的量级。

**参考答案**

1. `python3 code/03-error-model/error_model.py --trials 400`：fp16 的比值约
   0.53/0.54/0.58/0.48，int8 约 1.47/1.27/1.32/1.30（K=64/256/1024/4096）。
2. 把 `EQUIVALENT_U["int8"]` 改成 `1/127`，四个比值变成约
   `0.74 / 0.64 / 0.66 / 0.65`；改成 `1/(2√12·127)` 则变成约
   `5.1 / 4.4 / 4.6 / 4.5`。
   三个取法都不改变“数量级”这个结论，但 `1/(2·127)` 与 `1/127` 都落在
   1 的两倍以内，`1/(2√12·127)` 明显偏小。
   原因：均匀量化误差的**最坏值**是 `Δ/2`、**均方根**是 `Δ/√12`，
   两者相差 `√12/2 ≈ 1.73`；而点积误差里两个操作数都在量化，
   又会带来一个约 `√2` 的放大。工程上取 `1/(2 qmax)` 作为“等价 u”是与
   浮点格式 `2^-p` 口径一致的保守选择（两者都是“单元素相对上界”）。
3. `--rows 64 --cols 4096` 下 MXFP8 的相对 L2 是 `2.652e-02`，
   默认 `256×1024` 下是 `2.685e-02`，几乎不变。
   原因：MX 的 scale 是 **per-32-元素块** 的，块内的相对误差分布与张量整体
   尺寸无关，所以把形状换掉不改变误差的量级。
   对照 per-tensor int8：形状一变，absmax 跟着变，相对 L2 从 `4.95e-2`
   变成 `3.40e-2`。
4. 验证“E8M0 缩放精确”的思路：对随机的 fp32 值 `x` 与随机的 E8M0 scale
   `s = 2^k`，比较 `x / s` 与“先分解再重组”的结果。关键代码：

   ```python
   import numpy as np
   rng = np.random.default_rng(0)
   x = np.exp(rng.uniform(-20, 20, 100000)).astype(np.float32)
   k = rng.integers(-20, 20, 100000)
   s = np.ldexp(np.ones_like(x), k.astype(np.int32))   # 2^k
   q = x / s
   # 除以 2^k 精确 <=> 乘以 2^-k 精确 <=> 指数整体平移
   back = q * s
   print(np.array_equal(back, x))          # True：没有舍入
   ```

   结论：只要不触到 fp32 的指数上下界（`2^-126` 与 `2^127`），
   E8M0 缩放是精确的，`back == x` 逐位相等。

**常见错误**：以为“改 u 的定义可以改变实测值”。实测值由数据与量化方案决定，
改的只是分母。

## E12

**思路**：先按第 5.3 节的基线表估量级，再按第 5.1 节的三种参照设计验证方案。

**参考答案**

1. 权重按 per-channel 量化到 e4m3，主要误差来自 e4m3 的表示误差
   （`u = 6.25e-2`）；激活是 fp16，误差可忽略；累加在 fp32，也基本可忽略。
   所以预期相对 L2 在 `1e-3 ~ 1e-2` 量级（参照 `code/02` 里 MXFP8 的 2.7e-2，
   per-channel 的粒度更细一些，会更小）。
2.
   * 绝对参照（量化感知 fp64）：证明 kernel 的整数/浮点路径与 epilogue 都对；
     不能证明“量化方案好”。
   * 框架相对参照（例如 PyTorch 的 fp8 实现）：证明两个独立实现一致；
     不能证明任一方正确（E 行的假阳性就是这么来的）。
   * 量化前参照：只能回答“量化损失了多少”，不能当对拍判据（D 行）。
3. 关键实现（可在 `code/04-vs-reference/reference_matching.py` 的基础上改造）：

   ```python
   wq = quantize_e4m3_per_channel(w)        # 每行一个 scale
   got = (x @ wq.T).astype(np.float64)
   ref_abs = (x.astype(np.float64) @ wq.T.astype(np.float64))
   ref_fw  = torch.matmul(x, wq.T).double()          # 框架实现
   ref_pre = x.astype(np.float64) @ w.T.astype(np.float64)   # 量化前
   print(rel_l2(got, ref_abs), rel_l2(got, ref_fw), rel_l2(got, ref_pre))
   ```

4. 建议 `rtol=1e-2, atol=1e-3, max_mismatched_ratio=1e-3`（与
   `torch_assert_close` 的缺省一致）。理由：预期误差量级是 `1e-3 ~ 1e-2`，
   `rtol=1e-2` 覆盖它；`atol=1e-3` 兜住接近零的输出；
   `max_mismatched_ratio` 允许少量离群元素。**不要**为了通过而放到 `1e-1`，
   那会连“scale 用错轴”都放过（B 行只有 0.21 的相对 L2）。
5. 例如把 per-channel 的 scale 作用到 K 维而不是 N 维（乘错轴）：
   相对 L2 会跳到 1e0 量级、不匹配比例接近 1，而且误差在 N 方向上呈现
   “每个通道一个固定倍数”的结构。**先看相对 L2**（一秒判断是不是量级错误），
   再用“按行/列取 max”定位。

**常见错误**：只写一个参照。两个都错、错得一致的实现会一路绿灯（E 行）。

## E13

**思路**：用“误差 / 结果量级”+“误差的结构”两个维度分类。

**参考答案**

1. **正常数值误差。** 相对 L2 = 1.1e-1 正好是 int4 权重的量化误差量级
   （第 5.3 节基线表：int4 是 5e-2~2e-1），max err 也在结果量级。
   第一步：确认参照实现了同样的量化（不是拿 fp32 权重当参照）；
   若已是量化感知参照，则这说明 94% 的元素都在误差容差内近邻，属正常。
2. **逻辑错误（索引/scale 用错轴）。** 相对 L2 接近 1、几乎全错，
   且差异在 N 方向呈现固定倍数。这是“每个输出通道乘了不同的错 scale”的特征。
   第一步：检查 scale 的展开方式（per-channel 的 scale 有没有按 N 广播），
   以及 group 下标是否与 K 对齐。
3. **累加器精度不足。** 换 fp32 累加器后误差掉 4 个数量级，
   说明问题与输入无关。第一步：把累加器改成 fp32；若 K 很长且必须用低精度累加，
   就改成分段累加（split-K）。
4. **逻辑错误（反量化位置或 scale 索引随 K 错位）。** 误差与 K 的位置强相关，
   说明某一批 K 块用了别的块的 scale。第一步：把 scale 的下标表达式与 K 循环变量
   对照着看，确认每一块乘的是自己那组。
5. **正常数值误差。** 相对 L2 在 1e-3 量级、不匹配比例极低、误差无行列结构，
   符合 fp16/bf16 在中等 K 下的预期。第一步：不用改，确认容差与方法学一致即可；
   若汇报给人，说明这是量化误差而不是 bug。

**常见错误**：把所有失败都当成“精度不够”去放宽容差。第 2、4 组放宽容差也过不去。

## E14

**思路**：MoE 的约束是“参数在专家上、路由对数值敏感、分组 GEMM 的 scale 布局更复杂”。

**参考答案**

1. 顺序：**专家权重 → KV cache（若有长上下文）→ 激活 → 路由权重**。
   判据分别是：专家权重占显存比例最大且算术强度低（memory-bound，收益接近线性）；
   KV cache 是长上下文的显存瓶颈；激活量化只在 compute-bound 的形状上值得
   （见第 6.1 节）；路由只有极小的参数量，量化收益最小而风险最大。
2. 应该。路由（gate）的输出直接决定 top-k 选择，量化它可能选出不同的专家，
   表现为整段输出结构不同而不是误差变大。这是**离散错误**，无法用容差衡量。
   所以路由通常保持 fp32/fp16；专家权重可以放心用 int4/MXFP4。
3. 普通 GEMM 的 SFA / SFB 是“按行”的 group-major
   （`SFA[sf_group * M + m]`）。分组 GEMM 里 SFA 仍是“按拼接后的 M”，
   但 SFB 要按 `(E, N)` 组织：

   ```text
   SFA[sf_group * M_total + m]
   SFB[sf_group * E * N + eid * N + n]
   ```

   （`examples/blockscaled_gemm_sm100/mxfp8_illustrated.md`）
   多出来的 `eid` 维度是 scale 布局最容易写错的地方。
4. 分两层看：**逐层**用相对 L2 + 逐元素 max err + 不匹配比例
   （第 5.2 节的三个指标），保证每个 kernel 的实现是对的；
   **端到端**用 ppl / 任务准确率（例如 `examples/bitnet-1.58b/eval_ppl.py`），
   保证误差没有在几十层里累积到影响模型。两者缺一不可：逐层都过但 ppl 掉了，
   说明量化方案本身需要调整；ppl 没掉但某一层误差量级异常，
   说明那个 kernel 迟早会在别的输入上出问题。

**常见错误**：把“专家数多”直接等同于“可以放心大胆量化”。
专家权重可以，路由不行；两者的敏感度差一个数量级。
