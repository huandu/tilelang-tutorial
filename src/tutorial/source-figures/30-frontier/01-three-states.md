# 图 1：三种状态与判定流向（自绘）

## 三种状态的定义

```text
                       上游历史（从左到右）
  ───────────────────────────────────────────────────────────────────────────▶

   v0.1.14                v0.1.15                      main                 未合入分支
   (上一个 release)        (本书基线)                   (每天都在动)          (PR / RFC)
      │                       │                            │                     │
      │                       │                            │                     │
      └──── A 档 ─────────────┘                            │                     │
        v0.1.15 已具备                                     │                     │
        「可以写进教材、可以依赖」                          │                     │
                                                           │                     │
                              └──────── B 档 ──────────────┘                     │
                                仅 main                                        │
                                「下一个 release 会带上，现在不能依赖」          │
                                                                                 │
                                                          └──── C 档 ────────────┘
                                                            仅未合入 PR / RFC
                                                            「方向，不是能力」

  D 档（必须存在的一档）：
    无法确认 —— 资料没覆盖、或 PR 页面状态与代码快照矛盾。
    写「无法确认」是正确结论，不是偷懒。
```

## 一条能力的判定流向

```text
     问：这个能力能用吗？
              │
              ▼
   在 v0.1.15 里搜符号 ──命中──▶ A 档：v0.1.15 已具备
              │
            未命中
              │
              ▼
   在 main 快照里搜符号 ──命中──▶ B 档：仅 main
              │
            未命中
              │
              ▼
   在 PR / RFC 快照里搜符号 ──命中──▶ C 档：仅未合入（并注明快照日期）
              │
            未命中
              │
              ▼
           D 档：无法确认
```

## 三条容易搞错的地方

1. **“文档里有”不等于“release 里有”。** 章节里出现的能力名，必须在
   `_vendor/tilelang-v0.1.15/` 里能搜到符号才算 A 档。
2. **“issue 很老”不等于“早已落地”。** issue 号小只说明提得早；`#2115` 的
   PR 清单大部分已经合入，而 `#2196` 提得更晚却完全没动。判断只看代码。
3. **A 档不代表“本次新增”。** `reducer v2`（RFC #2897）在 `v0.1.14` 里就已经存在，
   把它写成“v0.1.15 新增”是错的。所以判定流程里必须有第 2 步的对照。
