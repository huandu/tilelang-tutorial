# 图 03 · static 与 continuous batching 的时间线

```text
static batching（凑满一批一起跑到底；每格 = 1 个 decode step）

  slot 0  ▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░░░   请求 A（8 步）做完后空占
  slot 1  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░   请求 B（18 步）
  slot 2  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓   请求 C（34 步）
  slot 3  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓   请求 D（34 步）
          └────────── 整批等最长的那个 ──────────┘
          下一批请求只能在整批结束后才开始 → 队头阻塞

continuous batching（每个 step 结束就能换人）

  slot 0  ▓▓▓▓▓▓▓▓████████████████████████   A 走后立刻补进新请求
  slot 1  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓██████████████   B 走后补新请求
  slot 2  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓██   C 仍在跑
  slot 3  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓██   D 仍在跑
          ↑ 每格都在换人，槽位利用率接近 1
```

| | static batching | continuous batching |
| --- | --- | --- |
| 谁决定一步的耗时 | 这一批里最长的序列 | 这一批里所有在跑的序列 |
| 早完成的序列 | 空占槽位，陪跑 | 立刻让位 |
| 新请求 | 等整批结束 | 下一个 step 就能进来 |
| kernel 的要求 | 固定长度即可 | 变长 batch、paged KV、prefill/decode 混步 |

**仿真里差多少。** `code/04-serving-schedule-sim/serving_schedule_sim.py`
在「decode step 固定 8 ms、prefill 12 us/token、64 个请求、8 个槽位、
输出长度离散」的人为参数下，continuous 的总耗时是 static 的 1/2.74，
吞吐 2.74×，平均 E2E 延迟从 12084 ms 降到 3953 ms。
**这组数字是仿真输出，不是测量**；换成别的参数结论的倍数会变，方向不变。

**注意「吞吐」和「延迟」在这里同时变好**，这是调度层面的收益；如果槽位被
占满，再加并发只会让排队延迟变长——那才是吞吐与延迟的权衡所在。
