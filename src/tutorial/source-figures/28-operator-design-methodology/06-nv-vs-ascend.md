# 图 6：NV 与昇腾的方法论差异

**用途**：正文第 5.4 节。三条线，容量、执行体、同步，如何改变设计选择。

```text
                          NVIDIA (sm_90)                    昇腾 (Ascend 950)
  -----------------------+---------------------------------+---------------------------------
  谁来算                  | warp / warpgroup                 | 一个 AI Core = 1 Cube + 2 Vector
                         | (SIMT，同一段代码所有线程)        | (Cube 与 Vector 是两块执行体)
  -----------------------+---------------------------------+---------------------------------
  片上容量谁决定 tile     | shared memory 容量               | L1 / L0A / L0B / L0C / UB 各自独立，
                         | + 寄存器堆 65536/SM              | 各自有对齐约束
                         | + 每线程 255 个寄存器上限         | L0A/L0B 512 B、L0C 64 B、UB 32 B
  -----------------------+---------------------------------+---------------------------------
  第一约束通常是谁        | 寄存器（累加器）与 shared        | GM→L1 的 MTE2 带宽（见下）
  -----------------------+---------------------------------+---------------------------------
  平衡判据               | 每线程寄存器数 ≤ 255，            | M*N/(M+N) >= cube_throughput/mte2_bw
                         | 每 SM 驻留块数 ≥ 2               | （本例 81.92，方形 tile 边长 ≥ 164）
  -----------------------+---------------------------------+---------------------------------
  调度怎么做             | 数据流注解（stage/order）        | 任务 + latency + II + 资源掩码 → Z3 求解
                         | + InjectSoftwarePipeline         | → PrepareMultiBuffer/Materialize
  -----------------------+---------------------------------+---------------------------------
  同步                   | 异步拷贝自带等待 + barrier       | InsertSync 统一插成对 Set/Wait flag
                         | 用户基本不写                     | 用户也基本不写（顺序写在代码里）
  -----------------------+---------------------------------+---------------------------------
  特殊的并行手段          | cluster / DSM / TMA multicast    | Cube 与 Vector 的核间流水
                         | warp specialization              | dual_copy / SimtVF / SimdVF
  -----------------------+---------------------------------+---------------------------------
  超低精度               | fp8（mma e4m3/e5m2，m16n8k16）   | fp8 走 Cube（16384 ops/cycle）；
                         | MX 块缩放                        | mxfp4 走 MX MAD（32768 ops/cycle）
  -----------------------+---------------------------------+---------------------------------
```

## 三条线各自改变什么设计选择

| 差异 | 它改变的那个决定 |
| --- | --- |
| **容量**：昇腾把片上存拆成 L1/L0A/L0B/L0C/UB 五块，每块有自己的对齐 | tile 尺寸不是“一个数放不放得下”，而是“每条数据该住在哪一块”；512 B 对齐会直接改掉合法的 K |
| **执行体**：Cube 与 Vector 是两块执行体 | “把 epilogue 融进 GEMM”在 NV 上是省一趟 HBM，在昇腾上还多一层意思，**用 Vector 的时间盖住 Cube 的时间**（`dual_copy` + `T.SimtVF`） |
| **同步**：昇腾是 pipe 到 pipe 的事件，不是线程屏障 | 加一条新的数据流 = 加一对 flag。设计时要问“这条依赖值得一次同步吗”，而不是“要不要加 barrier” |

## 一个具体的对照：同一个 tile 在哪条 pipe 上瓶颈

```text
   tile             NV 侧关注点                 昇腾侧（code/07 的模型）
   --------------+---------------------------+--------------------------------
   128x128x32    | shared 24 KB，regs 128/线程| MTE2 II 164 > Cube II 128
                 | -> 2 blk/SM               | -> GM→L1 是瓶颈
   256x224x128   | shared 192 KB（3 级流水）   | Cube II 1792 > MTE2 II 1229
                 | -> 1 blk/SM               | -> Cube 是瓶颈
   --------------+---------------------------+--------------------------------
   同一份「大 tile」在两边成立的理由不一样：
   NV 侧为了少读 HBM，昇腾侧为了喂饱 Cube。
```
