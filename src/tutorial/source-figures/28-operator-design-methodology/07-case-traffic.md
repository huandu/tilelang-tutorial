# 图 7：案例的流量账

**用途**：正文第 6.3–6.5 节。QK-Norm + RoPE + fp8 量化，4096 token。

```text
 0        60       120      180      240      300  MB
 |---------|---------|---------|---------|---------|--->  （每格 5 MB）

 理想      ==============             14 格   67.76 MB   (1.00x)
 下界      ^^^^^^^^^^^^^^

 A: 一行   ================================================================  63 格
   一 block ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^  315.23 MB  (4.65x)

 B: 8 行   ===================          19 格
   一 block ^^^^^^^^^^^^^^^^^          95.03 MB   (1.40x)

 C: 一 token ==============             14 格
             ^^^^^^^^^^^^^^             69.86 MB   (1.03x)

 `=` 是 payload，`^` 是 lookup。每一列的分解：

   理想   payload  63.57 MB   lookup   4.19 MB
   A      payload  63.57 MB   lookup 251.66 MB   <- 全部超出的部分都是查表
   B      payload  63.57 MB   lookup  31.46 MB
   C      payload  63.57 MB   lookup   6.29 MB

 payload 三列完全相同：三种设计算的东西一模一样，
 差别只在 norm 权重和 RoPE 表被重复读了多少次。
```

## 诊断路径

```text
  实测比下界慢 N 倍
        |
        +-- 实测带宽接近峰值吗？
              |
              +-- 是 --> 这个 kernel 搬的字节比算法需要的多
              |         -> 回到图 7，找 lookup 的重复次数
              |
              +-- 否 --> 不是流量问题：去查 occupancy、尾波、流水深度
                        （第 4 节与第 11 章）
```

## 三个设计与它们的修复动作

| 设计 | 相对下界 | 要改什么 |
| --- | --- | --- |
| A：一行一 block | 4.65× | 把一个 token 的多行放进同一个 block，让查表被摊开 |
| B：8 行一 block | 1.40× | 继续加大行数，直到一个 token 的 q 与 k 都在同一个 block 里 |
| C：一 token 一 block | 1.03× | 剩下的 3% 是每个 token 各读一遍权重与表；就是下界本身 |
